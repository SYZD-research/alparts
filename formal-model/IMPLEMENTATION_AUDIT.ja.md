## 1. M2の対象外のチャンネル変更で、上位メンバーの閲覧権が失われる

再現検査：`M2c-privacy`、`M2c-category-move`。

1. オーナー、順位90の上位メンバー、順位60で `MANAGE_CHANNELS` を持つ管理者を作る。
2. 全員が閲覧できる公開チャンネルを、順位60の管理者が非公開に変更する。
3. 実装はその管理者だけを非公開チャンネルのメンバーにする。オーナーと上位メンバーは閲覧できなくなる。

別の検査では、上位メンバーのロールに `VIEW_CHANNELS` のdenyがあるカテゴリへ同じ管理者がチャンネルを移動すると、その上位メンバーの閲覧権が失われました。

[channel.service.ts](../packages/server/src/services/channel.service.ts) の `updateChannel` は閲覧者の変更と鍵更新を計算しますが、`assertNoSuperiorAccessLoss` を呼びません。一方、既存の非公開チャンネルから上位メンバーを直接削除する操作は、同じ関数により拒否されました（`M2c-private-remove`）。

**これは、M2が列挙した遷移についてのPASSを否定する結果ではありません。** M2に公開範囲変更・カテゴリ移動の遷移がないため、H2/H3をすべての管理操作に拡張できないという範囲の欠落です。これらの操作にも同じ階層保護を求めるなら入口のガードとモデルの遷移の両方が必要です。許容する方針なら、保証の説明に例外を明記する必要があります。

## 2. M3の通常提案の条件と、実際のHTTP経路が一致しない

再現検査：`M3c-orphan-proposal`。

1. 移行済みの旧鍵エポックを持つチャンネルを用意する。
2. その鍵を持つメンバーが閲覧者から外れ、鍵を持たず管理権限もないメンバーだけが残る。
3. 実装の事前判定は `historyRecoveryRequired=true`、`canRotate=false`。
4. 残ったメンバーの実際の端末署名・MLSパッケージ・セッションを用い、**fresh-startの署名も追加確認も送らず**、通常の `POST /api/channels/:id/mls/epochs` に提案する。
5. **HTTP 201** で受理される。

[m3_key_epochs.py](./m3_key_epochs.py) の通常提案は、保持者がいない場合でも管理者に限ります。[key.service.ts](../packages/server/src/services/key.service.ts) の `getKeyRecipientsFromStore` の `canRotate` も同じです。しかし実際の書き込み側では、`historyRecoveryRequired` の場合に「送信者が旧エポックを受領したか」の拒否条件を外し、管理権限のチェックを復元していません。

fresh-startでは追加確認と、管理者でない人による再開の通知対象計算を行います。通常提案の経路はその分岐を通りません。HTTPで確認したのは追加確認なしの受理です。通知対象が空になる点は、返却値を作る分岐とルートのコードを照合しました。

影響は、モデルにない経路で会話の再開処理を開始できることです。この検査で旧メッセージの復号や第三者への鍵漏えいが確認されたわけではありません。

## 3. M6 A3の「実際に変更した後」という条件を、並行した同一保存がすり抜ける

再現検査：`M6c-concurrent-noop`。通常の逐次同一保存を拒否する対照検査 `M6c-noop` は成功。

1. 表示名Aに対して、Bへの保存要求1が現在値Aを読む。その直後に処理を一時停止する。
2. 保存要求2がBを保存し、管理者がそのプロフィールに警告する。
3. この時点では解除依頼が `PROFILE_APPEAL_NEEDS_CHANGE` で拒否されることを確認する。
4. 保存要求1を再開する。既にBであるのに再度Bを書き、`profileUpdatedAt` が警告後へ進む。
5. 警告後に内容を変更していないのに、解除依頼が成功する。

[profile.service.ts](../packages/server/src/services/profile.service.ts) の `updateProfile` は、変更の有無を**監査トランザクションに入る前**に調べています。グローバルな監査直列化は、この先行する読み取りを保護しません。

検査で差し替えたのは「実DBの先行SELECTが終わった後、結果を呼び出し側へ返すタイミング」だけです。書き込み、行ロック、監査、コミット、解除依頼の判定は実装とPostgreSQLをそのまま実行しています。モデルのeditは1つの原子的な遷移なので、この順序を表せません。

解除依頼の生涯1回制限や、警告そのものの自動解除は突破していません。変更の有無の再確認を、直列化された更新の中に入れる必要があります。

## 4. 同じ画素の画像が、異なる画像として保存される

再現検査：`M6c-png-canonical`、`M6c-same-pixels`。

- 256×256の同じRGBA画素を、PNGのNoneとSubの行フィルタでそれぞれ正しく符号化する。
- どちらも受理されるが、サニタイズ後のバイト列が一致しない。
- None版を保存して警告した後、None版の再送では解除依頼は拒否される。
- 画素を変更せずSub版へ符号化し直して送ると、解除依頼が成功する。

[profile-input.ts](../packages/server/src/security/profile-input.ts) はzlibを展開しますが、PNGの行フィルタを戻していません。フィルタ付き走査線をそのまま再圧縮しており、コメントにある「equal pixels give equal bytes」は成立しません。`isCurrentAvatar` はバイト列で比較するため、見た目の変わらない再送でA3の前提が崩れます。

既存のE2は、余分なチャンクや圧縮ストリーム後方のバイトが残らないことを検査しています。同じ画素の正規化を検査していないため、この問題でもPASSになります。行フィルタを復元した画素を一定の形式で符号化するか、画素の比較が必要です。

## 5. M1の入力範囲と、内部の整数バリデータに差がある

再現検査：`M1c-validation-width`。

`assertValidPermissionMask` と `assertValidChannelOverrideMask` は、`2**32`、`2**32+64`、`2**40` を受理します。JavaScriptのビット演算が上位ビットを切り捨てるためです。M1は32bitのビットベクトルに範囲制約を置くため、これらの入力を扱いません。

**HTTPからの権限昇格の再現ではありません。** 対応ルートのZodスキーマは `0x7fffffff` 以下に制限しており、DBの格納先もintegerです。内部関数の検証契約とモデルの適用範囲の差として記録します。ビット演算の前に数値の上限も確認すると、モデルの前提を関数自身で保証できます。

## 6. 既知のAU4bは実装でも再現

再現検査：`M5c-AU4a`、`M5c-AU4b`。

過去のチェックポイントを戻すと、稼働中のプロセスは拒否し、その後の監査対象書き込みも停止します。一方、DB管理者が末尾の監査行を削除し、対応する過去のチェックポイントを戻して新規プロセスで検証すると、`valid=true` が返ります。

必要な能力は、DB管理者として追記専用制約を回避できること、チェックポイントの過去コピーと書き換え権限、再起動です。今回の直接照合では外部witnessを設定していません。これは既存のR-047 / M5 AU4bに一致する既知の限界で、新規の発見とは数えていません。

## 検証器で修正した誤PASS

修正前の振る舞いは、プロセス結果やZ3応答を差し替える負の検査で再現しました。

| 入力した異常 | 修正前 | 修正後 |
| --- | --- | --- |
| Node/tsxがない | M1c C1がPASS | MODEL-GAP、終了1 |
| 400ケースに対して先頭10件だけ返す | `zip`で残りが捨てられ、C0/C1ともPASS | 件数・ユーザー・チャンネルの完全性を検査、MODEL-GAP |
| PNGコーパス結果が空配列 | E1/E2/E3がすべてPASS | 固定22件・名前・期待値・結果型を検査、MODEL-GAP |
| Z3が`unknown`を返す | `sat`でないのでHOLDSをPASS | `unsat`と区別し、MODEL-GAP |

権限定数も実装と照合し、M2cでは実際の階層保護関数を呼びます。実装側を故意に弱めたときの対照検査も残しています。PNG E3の表現も、実際に検査している「このコーパスの展開爆弾を500ms以内に拒否」に限定しました。

## 残る検証範囲の制約

- M1は3ロール×32bitの制約内での記号的検証。30,000ワークスペースの差分検査は実装との強い対応確認ですが、任意の実装入力の証明ではありません。
- M2は列挙した操作・初期状態と探索深さに限定。M2cは保護関数の一致を調べますが、すべての呼び出し経路への適用は保証しません。
- M3は3利用者・4端末・最大4エポック、閲覧者変更と端末変更が各2回。24時間のエポック寿命はモデルにありません。停滞エポックのabortをモデルが無条件に生成する一方、実装は管理権限等を確認します。非管理者による停滞後のfresh-startの扱いも異なり、到達可能性による復旧の保証には実遷移との追加照合が必要です。
- M4は最大4セッション、各主体の端末登録を1台までに制限しています。正常な複数端末の追加・再登録を含む全履歴の証明ではありません。
- M5は暗号の安全性を仮定した4行の構造的モデルです。実装の署名安全性そのものを証明していません。
- M6bは行ロックを外すと並行依頼が通る対照モデルですが、現在の単一ランタイムでは監査のグローバルな直列化もあります。「行ロックだけを外した実装で必ず再現する」という意味ではありません。画像保存の曖昧コミットについては、実DBでコミット成功後にエラーを注入し、新しい画像が読み出せることも確認しました。

## 再実行

リポジトリルートで、Node >=24.8、インストール済みのpnpm依存関係、ビルド済みshared、Z3が必要です。

```bash
python3 -m unittest discover -s formal-model -p 'test_*.py' -v
python3 formal-model/run.py
python3 formal-model/conformance.py --cases 10000 --seed 20260929
python3 formal-model/conformance.py --cases 10000 --seed 1
python3 formal-model/conformance.py --cases 10000 --seed 4294967295
```

`run.py` は既知AU4bをFINDINGとして保持しているため終了1です。実行環境が不足したときも終了1になり、MODEL-GAPとして区別されます。

実サービス照合には、使い捨て環境の `DATABASE_URL`（DB作成権限、DB名は `alparts_test*` または `alparts_security_test*`）、`MINIO_ENDPOINT`、`MINIO_PORT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET`、およびテスト用の `JWT_SECRET`、`PASSWORD_PEPPER`、`AUDIT_INTEGRITY_KEY` を設定します。Originは `http://localhost:5173` を許可します。

```bash
cd packages/server
RUN_FORMAL_CONFORMANCE=1 NODE_ENV=test \
  node --import ./node_modules/tsx/dist/loader.mjs \
  ../../formal-model/conformance/service-audit.mts
```

本体が今回の対象リビジョンなら、14検査で6成功・8反例、終了1になります。準備失敗や予期しない実行エラーは終了2です。反例を期待値として成功扱いに変えてはいません。本体の修正後は、それぞれの正しい性質が成り立つと対応する検査がPASSになります。

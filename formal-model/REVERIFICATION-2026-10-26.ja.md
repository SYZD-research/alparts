## 新しい所見：M3s KS-sound

管理者は、fresh start の条件 (c) を、何も15分待っていないうちに使えることがあります。

```text
Y1: publish package
authz: Z gains view
Z1: publish package
clock: the 24-hour genesis wait ends
Y1: genesis with {Y1,Z1}
authz: Y loses view
clock: 15 minutes pass
X1: publish package
authz: Z loses view
authz: Y gains view
X1: fresh start: manager, changes stalled with {X1}
```

- **起きること：** グループの `remove_required_at` は、メンバーの利用者が最初にチャンネルを見られなくなったときに設定されます（`refreshGroupRemoveRequirement`、key-epoch-state.ts）。そのようなメンバーが残る間は `coalesce` で元の時刻が保たれます。Y が見られなくなってから15分後に Z も見られなくなり、その後 Y が戻ると、Z1 の削除は Y の時刻から数えられます。グループの外にある管理者の端末 X1 は、Z1 の削除がまだ数分しか待っていないのに、条件 (c) でグループを置き換えられます。`pendingSince` の説明（閲覧権を失ったメンバーは、閲覧権を失った時から数える）とも食い違います。
- **影響：** 小さい。機密性は変わりません（M3 の KC は、待ち時間をまったく課さないガードで成り立つ）。fresh start には MANAGE_CHANNELS と本人確認が必要で、15分待てば同じ fresh start ができます。置き換えられたグループのメンバーは、新しいグループに Welcome から参加します。
- **提案：** メンバーごとに閲覧権を失った時刻を持ち、削除はそれぞれの時刻から数える（スキーマの変更が要る）。スキーマを変えない案として、他にそのようなメンバーが残る間にメンバーの利用者が閲覧権を取り戻したら、時刻を設定し直す。こちらは条件 (c) を遅らせることしかない。どちらにするかは設計の判断なので、[RISK_REGISTER](../docs/RISK_REGISTER.md) の R-057 に載せました。
- **修正：** 同日、1つ目の案で修正しました（[追記](#追記r-057-の修正)）。

## 追記：R-057 の修正

M3s KS-sound の所見（R-057）を、提案の1つ目の案で修正しました。本番運用の前なので、スキーマを変えています。

- **実装：** グループで1つの `mls_groups.remove_required_at` をやめ、メンバーごとに `mls_group_members.access_lost_at` を持たせた（マイグレーション 0026）。時刻は `refreshMemberAccessLoss`（key-epoch-state.ts）が更新する。利用者がチャンネルを見られなくなると、その利用者のメンバーに時刻を設定する。見られないままの間は時刻を保ち、また見られるようになると消す。`pendingSince` は、閲覧権を失ったメンバーの削除を、そのメンバーの時刻から数える。失効した端末は、これまでどおり失効の時刻から数える（両方あるときは失効の時刻）。
- **既存のデータ：** 0026 は、`remove_required_at` が設定されていたグループの現在のメンバー全員に、移行した時刻を設定する。誰がいつ閲覧権を失ったかは記録されていなかったため。これで条件 (c) が早まることはなく、遅れることしかない。利用者がまだ見られるメンバーにも時刻が入るが、その時刻は読まれない。失効していないメンバーの削除が必要になるのは利用者が見られなくなったときで、そのときに新しい時刻が設定されるため。
- **モデル：** M3s のサーバーの時刻を、メンバーごとの時刻に改めた。修正前の動作（グループで1つの時刻）は、対照 KS-loss-ctl として残した。
- **結果：** M3s は **PASS 6**（640,929状態、約1分）。KS-sound は PASS になった。KS-loss-ctl は、上の所見と同じ11手の反例を再現する。KS-keep と、ほかの対照3件の結果は変わらない。検証器の回帰テストに、この11手を両方の規則でたどる1件を加えた（27件成功）。
- **実装のテスト：** 単体テスト（mls-group-rules.test.ts）に、取り消された先の閲覧権の喪失の時刻を使わないことを確かめる1件を加えた。統合テスト（integration.test.ts）では、bob、carol の順に閲覧権を失い、bob が戻った後も carol の時刻が carol のものであることを、実際の DB で確かめた。サーバーの単体テストは235件成功（1件は既定でスキップ）、統合テストは26件、アカウントの統合テストは27件成功。統合テストのうち監査チェックポイントの書き込み失敗の1件は、ディレクトリの書き込み権限を外して失敗を起こす。この環境は root で動くため、そのままでは失敗を起こせない。root の権限の例外（CAP_DAC_OVERRIDE）を外して実行し、成功を確かめた。実サービス照合は36成功 / 反例0のまま。
- **移行の確認：** 0025 までを適用した DB に、`remove_required_at` が設定されたグループと設定されていないグループを入れた。そのうえで dev.sh と同じ `pnpm --filter @alparts/server exec tsx src/scripts/migrate-runtime.ts` を実行した。前者の現在のメンバーにだけ時刻が入り、削除済みのメンバーと後者のメンバーには入らないこと、列が消えることを確かめた。dev.sh は起動のたびにこれを実行するが、2回目の実行は何も変えない。移行した DB のスキーマの指紋（`expectedSchemaCatalog`）は、新しく作った DB と一致した。dev.sh そのものは、Docker が使えない環境のため実行していない。

## 実サービス照合の追加

| 検査 | 方法 | 修正前 |
| --- | --- | --- |
| M4c-device-limit | 最初の端末（承認済み）の後に、未承認の端末7台で上限の8台を埋める。所有者が端末を1台加え、最も古い未承認の端末だけが退き、そのセッションが終わり、ディレクトリに `expire` が記録されることを確かめる。続けて運用者のリセットが未承認の端末をすべて退かせ、承認済みの端末を残すことを確かめる | 反例（`DEVICE_LIMIT_REACHED`、fe8c788） |

## モデル化していない気づき

- 使われていない `ThreadPanel.tsx` が使う `thread-model.ts` は、返信を署名されていない `refMessageId` でまとめ、検証も v5 の確認もしません。今は画面に出ないので問題になりませんが、使う前に M9 の投影と同じ扱いにする必要があります。
- M5v の目録の照合は、ソースの一重引用符の文字列からアクション名を集めます。テンプレート文字列で組み立てる名前（`permission-override.service.ts`、`role.service.ts`）は、目録に手で書いた分だけが対象です。
- AV-case は URL のパスの ID だけを調べます。リクエストの本文の ID が小文字だけであること（96f30de）は、`canonical-id.test.ts` の単体テストで確かめています。
- `removeChannelMember` のルートは `lostUserIds` だけを見て、`lostCallUserIds` を見ません。非公開チャンネルのメンバーの削除は見る権利そのものを外すので、今は問題になりません。

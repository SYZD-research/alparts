### モデル化していない気づき

- `channel.update` の監査行は、非公開チャンネルの設定変更で閲覧権を得た・失った利用者の ID を `details` に含み、管理イベントとして監査ログの閲覧者全員に見える。`forum.tag.*` の行もタグ名を含む。チャンネル内の活動を隠す方針（AV-class）とそろえるなら、これらの詳細の扱いを決める必要がある。
- SFU の WebRTC サーバーは作成のたびにポート番号を1つ進めるので、作成の失敗や worker の再起動の後は、設定したポート範囲（basePort から worker の数まで）の外で待ち受ける（[webrtc-server-manager.ts](../packages/server/src/voice/webrtc-server-manager.ts)）。SFU は既定で無効。
- サーバーの型検査（`tsc --noEmit`）は、[integration.test.ts](../packages/server/src/security/integration.test.ts) の長いテスト関数のフロー解析で、TypeScript の再帰の上限に近い。関係のないファイルを足しただけで "Maximum call stack size exceeded" で止まることがある（今回はテストの形を変えて避けた）。長いテストを分ければ解消する。

## 追補2：SFU 通話のフレーム暗号化（M8 VE2）

残っていた FINDING の M8 VE2（SFU を使う通話では、サーバーが通話音声を復号できる）に対応しました（[ADR 0014](../docs/adr/0014-sfu-frame-encryption.md)、R-052）。

当初の提案では、鍵をチャンネルの MLS グループから導出するつもりでした。しかし音声チャンネルには MLS グループがなく、テキストチャンネルのグループには通話に参加していないメンバーも含まれます。そのため、参加者が通話ごとに作る鍵にしました。参加者が変わるたびに鍵を替える（MEDIA-09）のにも、MLS の commit は要りません。

| 対象 | 対応 | 確認 |
| --- | --- | --- |
| M8 VE2（R-052） | 運用者が SFU を有効にすると、そのデプロイメントの通話はすべて SFU を経由する。<br>送信側のブラウザーのワーカーが、音声の各フレームを SFrame（RFC 9605、AES_128_GCM_SHA256_128）で暗号化してから送る。受信側は、届いたストリームの参加者の鍵で復号でき、カウンターがまだ使われていないフレームだけを再生し、ほかは捨てる。<br>鍵は参加者ごと・通話ごとの乱数で、受信端末の暗号鍵で包み、送信端末の鍵で署名して、参加者ごとに送る。参加・退出のたびに全員が鍵を替える。<br>フレームを暗号化できないブラウザーは参加せず、「このブラウザーでは通話を安全に行えないため、参加できません。ブラウザーかアプリを最新にしてお試しください」と表示する | VE2 が成り立ち、暗号化しない場合の VE2-ctl で破綻する。<br>鍵の交換は M8k（下記）で、実際の mediasoup と Chromium で6件を照合した（下記）。<br>SFrame の実装は、RFC のヘッダーの試験ベクトル289件と暗号化の試験ベクトルで確認した |

### M8k：通話の鍵の交換（新規）

A と B が通話中で、C が参加して退出する場面です。3つのクライアントで実際の鍵管理（[voice-frame-keys.ts](../packages/client/src/services/voice-frame-keys.ts)）を動かしました（[voice-keys-harness.mts](./conformance/voice-keys-harness.mts)）。

- 次の順序をすべてサーバーが選べるものとして、全探索しました：署名の完了、サーバーの応答、鍵を使い始める前の待ち、各鍵メッセージの配信（遅らせる・省く・2度目を配信する）、参加と退出の通知。
- 包みと署名は記号的に扱い、偽造できないものとしました。
- C は自分宛ての鍵メッセージを、退出後も含めてすべて読めるものとしました。

| 性質 | 内容 |
| --- | --- |
| KJ | 参加した者が受け取る鍵は、ほかの参加者がその参加を知った後に作った鍵だけ（参加前の音声は読めない） |
| KL | 退出を知った参加者は、退出した者に鍵を送らず、退出した者が受け取った鍵で送信を始めない（退出後の音声は読めない） |
| KR | 鍵は送信者ごとに1度だけ受け付ける。同じ送信者のより新しい鍵の後には受け付けず、作った参加者の鍵としてだけ受け付ける |
| KH | サーバーがすべてを配信し終えると、参加者は互いの現在の鍵を持ち、退出した者が受け取った鍵はどれも使われていない |

3構成（C の参加、C の参加で各メッセージを最大2度配信、C の参加と退出）で計 1,563,599 状態を探索し、違反はありませんでした。対照3件は、それぞれ対応する性質を破ります。

この探索の作成中に、鍵管理の競合を1件見つけて修正しました。

- **起きたこと（KL）：** 退出した参加者宛ての鍵を署名している間に退出の通知を処理すると、その鍵を退出した参加者へ送り、その後その鍵で送信を始めていた。
- **修正：** 署名の直後に、宛先がまだ参加中かを確かめ直す。鍵を送る間に宛先が退出していたら、その鍵は使わない。
- **回帰：** 修正前の動作を KL-ctl として残した。クライアントの単体テストも追加し、修正前のコードでは失敗することを確かめた。

### 検証器の修正

M8k と M8b（[voice-sfu-harness.mts](./conformance/voice-sfu-harness.mts)）の探索は、状態の指紋に、遷移の途中で記録した違反を含めていませんでした。そのため、違反を伴う経路と伴わない経路が同じ状態に至ると、先に探索した経路だけが残り、違反を見落とすことがありえました。

## 追補3：従来の形式の拒否（M9）

追補では、更新前のクライアントのために、従来の形式の参照とファイル署名をサーバーで受け付けたまま残し、LIMIT としていました。正式リリース前で、従来の形式に頼るクライアントがないため、これを拒否するようにしました（[ADR 0013](../docs/adr/0013-signed-message-references.md)、R-051）。

| 対象 | 対応 | 確認 |

| M9 MI-edit-legacy・MI-reply-legacy・MI-quote-legacy・MI-delete-legacy（R-051） | 編集・削除・引用と、フォーラムの投稿の中のイベントは、v5 でだけ受け付ける。<br>サーバーは従来の形式（v3/v4）の書き込みを拒否する。クライアントの検証も、参照を持つイベントは v5 でだけ確かめる（[message-envelope.ts](../packages/client/src/stores/message-envelope.ts)）。検証できない編集・削除は捨て、引用・返信は検証できないメッセージとして表示する。<br>署名済みの idempotency key がないメッセージは名指せないので、編集・削除・引用・返信を断り、「このメッセージは編集・削除・引用・返信できません」と表示する | 従来の形式の4件が成り立つ（HOLDS）。拒否する前のクライアントを対照 MI-legacy-ctl として残す。<br>結合テスト（従来の形式の編集・引用・削除と、フォーラムの返信を 400 で拒否）。クライアントの単体テスト（検証に使う形式の選択、名指せないメッセージ） |
| M9 MI-file-v2 | ファイルの署名は、メッセージの署名済み idempotency key を含む形式（v3）だけを受け付ける。key を含まない従来の v2 は、サーバーとクライアントの両方で拒否する | MI-file-v2 が成り立ち、拒否する前の動作を MI-file-v2-ctl として残す。結合テスト（v2 の署名を 400 で拒否）、単体テスト |

モデルの変更：これまでハーネスは、本物の署名ならクライアントの検証を通るものとしていました。今回からは、クライアントが実際に試す署名の形式（message-envelope.ts）で、本物の署名と照合します。従来の形式の履歴を、今のクライアントと、拒否する前のクライアント（対照）の両方で全列挙しました。

## 環境と再実行

Python 3.13.16、Z3 5.1.0、Node 24.21.0、PostgreSQL 16.15、SeaweedFS 4.47（S3 互換）を使用しました。DB は `alparts_test*` / `alparts_security_test*` の名前で新規に作って終了時に削除し、bucket もこの検査専用のものです。既存の開発用データと本番データには触れていません。認証情報は使い捨てのものを生成し、リポジトリには含めていません。

```bash
python3 -m unittest discover -s formal-model -p 'test_*.py' -v
python3 formal-model/run.py M1c M1 M2 M2c M3r M4 M4s M5 M5v M6 M7 M9   # 約5分
python3 formal-model/run.py M3                                           # 約6分、最大約0.9GB
python3 formal-model/run.py M8                                           # 4コアで約25分
```

M1c・M2c・M5v・M6・M8・M9 は Node >=24.8 と `pnpm install` 済みのリポジトリが必要です（`packages/server` の tsx ローダーを使用）。実サービス照合は、使い捨ての DB 管理者 URL、S3 互換の保存先、テスト用の秘密情報を設定し、`NODE_ENV=test` で `pnpm --filter @alparts/server test:formal-conformance` を実行します。DB 名は `alparts_test*` または `alparts_security_test*`、Origin は `http://localhost:5173` です。

SFU 通話の照合は、同じ設定に加えて Playwright（`PLAYWRIGHT_MODULE`、既定は `playwright-core`）と Chromium（`CHROMIUM_PATH`）を指定し、`pnpm --filter @alparts/server test:voice-e2e` で実行します。サーバーは mediasoup の worker を起動し、20000〜32000 のうち空いているポートで待ち受けます（OS が一時的な通信に使う範囲を避けるため）。`VOICE_E2E_CONTROL=plaintext-frames` を付けると、フレームを暗号化しない対照になります（フレームの検査が反例を報告し、終了コードは1）。M8k は4つの worker スレッドで探索します（M8 全体で約25分）。

### モデル化していない気づき

- `channel.update` の監査行は、非公開チャンネルの設定変更で閲覧権を得た・失った利用者の ID を `details` に含み、管理イベントとして監査ログの閲覧者全員に見える。`forum.tag.*` の行もタグ名を含む。チャンネル内の活動を隠す方針（AV-class）とそろえるなら、これらの詳細の扱いを決める必要がある。
- SFU の WebRTC サーバーは作成のたびにポート番号を1つ進めるので、作成の失敗や worker の再起動の後は、設定したポート範囲（basePort から worker の数まで）の外で待ち受ける（[webrtc-server-manager.ts](../packages/server/src/voice/webrtc-server-manager.ts)）。SFU は既定で無効。
- サーバーの型検査（`tsc --noEmit`）は、[integration.test.ts](../packages/server/src/security/integration.test.ts) の長いテスト関数のフロー解析で、TypeScript の再帰の上限に近い。関係のないファイルを足しただけで "Maximum call stack size exceeded" で止まることがある（今回はテストの形を変えて避けた）。長いテストを分ければ解消する。

## 追補：同日の追加対応

再検証の後、次の3点に対応しました。

| 対象 | 対応 | 確認 |
| --- | --- | --- |
| M9 MI-edit / MI-reply / MI-quote（R-051） | メッセージの形式 v5 を追加した。編集・削除・引用と、フォーラムの返信・編集・削除は、対象のメッセージ（フォーラムでは投稿の最初のメッセージ）を、サーバーの ID に加えてその作者と作者が署名した idempotency key でも指し、この組に署名する。サーバーは組を保存せず、参照先の行から求めて書き込みの検査と配信に使う（移行は不要）。クライアントは v5 のイベントを、署名した対象のメッセージにだけ適用・表示する。引用元が一致しないときは「元のメッセージを表示できません」と表示する。参照のないメッセージは従来の形式で署名するので、更新前のクライアントも検証できる（[ADR 0013](../docs/adr/0013-signed-message-references.md)） | M9 を v5 と従来の形式の両方で全列挙した（2場面 × 2形式、計748,220通り。各場面に削除を1件追加）。v5 では MI-edit・MI-reply・MI-quote と新しい MI-delete が成り立ち、正直な配信ではすべての参照が署名どおりに表示される（MI-honest。検査が空振りでないことの確認）。従来の形式の4件は LIMIT。サーバーの単体テスト（v5 の直列化の固定値、組の改ざん、不正な組み合わせ）、結合テスト（実 DB で、別のメッセージの組で署名した編集・削除・引用・返信を 400 で拒否し、正しい組では受理し、配信のすべての経路に組が付く）、クライアントの単体テスト |
| M4s AS3-pk（R-053） | 運用者のパスワードリセットで、アカウントのパスキーもすべて削除する（f5bac62）。端末は残す（失効には利用者の別の端末の署名が要るため、利用者がログイン後に知らない端末を失効させる） | AS3-pk が成り立ち、修正前の動作を AS3-pk-ctl として残す。アカウントの結合テスト |
| M5v AV-L-links（R-056 の一部） | 監査ビューがチェーンのハッシュ（prevHash、hash）を返さない（f5bac62）。閲覧者は監査鍵なしにハッシュを確かめられず、チェーンは全体で1本なので、見えない行が間にあることと時刻がわかっていた | AV-links が成り立ち、対照 AV-links-ctl。実サービス照合 M5c-view-chain-fields |

あわせて、[integration.test.ts](../packages/server/src/security/integration.test.ts) の型検査が再帰の上限に近い件は、原因が等値の検査の型（`asserts`）にあることを確かめ、絞り込みのない型で呼ぶようにして解消しました（1d2c6c4）。実サービス照合の後片付けでは、接続プールの終了を待たずに DB を削除すると終了コードが1になることがあったため、接続が閉じるのを待ってから削除するようにしました（検査の結果には影響しません）。

### 残る制限（M9）

- 更新前のクライアントが署名したイベント（v3/v4）と、idempotency key に署名する前のメッセージへの参照は、引き続きサーバーの ID だけで対象を指すため、付け替えられる（MI-edit-legacy・MI-reply-legacy・MI-quote-legacy・MI-delete-legacy）。
- 更新前のクライアントは v5 のイベントを検証できない。更新済みのクライアントによる編集・削除を反映せず、引用とフォーラムの返信を検証できないメッセージとして表示する。デスクトップ版と Android 版はクライアントを同梱するため、アプリの更新が必要。
- サーバーは新しい書き込みでも従来の形式を受け付ける。対象を v5 で示せる参照に従来の形式を拒めば、付け替えられるイベントを更新前に書かれたものに限れるが、更新前のクライアントの編集・削除・引用・返信は失敗するようになる。

## 環境と再実行

Python 3.13.16、Z3 5.1.0、Node 24.21.0、PostgreSQL 16.15、SeaweedFS 4.47（S3 互換）を使用しました。DB は `alparts_test*` / `alparts_security_test*` の名前で新規に作って終了時に削除し、bucket もこの検査専用のものです。既存の開発用データと本番データには触れていません。認証情報は使い捨てのものを生成し、リポジトリには含めていません。

python3 -m unittest discover -s formal-model -p 'test_*.py' -v

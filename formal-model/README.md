# formal-model — Alparts 設計検証モデル

Alparts のセキュリティ設計を、実装から写し取った規則で検証するモデルです。保証の対象は、各モデルに含めた状態と遷移の範囲に限られます。

実装照合で見つけた不一致を修正し、モデルと実サービスの回帰テストを追加しました。最新の結果は [2026-10-22 の修正後の再検証（2026-10-26）](./REVERIFICATION-2026-10-26.ja.md)、その前は [アーキテクチャ変更後の再検証（2026-10-09）](./REVERIFICATION.ja.md)、それ以前は [修正・再検証記録](./REMEDIATION.ja.md) と修正前の反例の [実装照合記録](./IMPLEMENTATION_AUDIT.ja.md) にあります。モデル内のPASSを実装全体の保証に拡張することはできません。

既定の `run.py` はデータベースに接続しません。M1c / M2c / M5v / M6e / M8b / M8k / M9 / M10 は実装のコードをローカルで実行します。別途 `conformance/service-audit.mts` は、明示的に指定したテスト環境内に新規データベースを作って実サービスを検査し、`conformance/voice-sfu-e2e.mts` は実際の mediasoup と Chromium で SFU 通話を検査します。

## 実行

```bash
pip install z3-solver          # M1 のみ使用
python3 formal-model/run.py                 # リポジトリルートから。M3は約7分・最大約0.9GB、M8は4コアで約1時間
python3 formal-model/run.py M1c M1 M2 M2c M3r M4 M4s M5 M5v M6 M7 M9 M10 # M3・M3s・M8以外（約20分）
python3 formal-model/run.py M3 M3s          # 約8分
python3 formal-model/run.py M3rQ M3sQ M10Q M4T   # Quint/TLC と Tamarin のモデル（約20分）
python3 formal-model/run.py M3Q             # 約1時間（6版の拡大探索を含む。M3Q_LARGE=0 で省略）
python3 -m unittest discover -s formal-model -p 'test_*.py' -v # 検証器の負の検査
```

`*Q` のモデルは quint と Apalache（TLC を含む）と Java 17 以降を、M4T は Tamarin と Maude を使います。導入は [quint/README.md](./quint/README.md) と [tamarin/README.md](./tamarin/README.md) にあります。

M1c / M2c / M5v / M6e / M8 / M9 / M10 は Node >=24.8 と `pnpm install`・sharedのビルド済みのリポジトリが必要です（`packages/server` の tsx ローダーを使用）。環境不足・出力欠落・判定不能はMODEL-GAPとなり、成功扱いにはしません。

## 判定の読み方

| 判定 | 意味 |
| --- | --- |
| PASS | 対象モデルの範囲で性質が成り立つ（HOLDS）。または、安全機構を外した弱化モデルで実際に破綻する（CONTROL）。後者は、対応する HOLDS 検査が空振りでないことの確認。 |
| LIMIT | 文書化済みの限界に、モデルが実際に到達する。到達できない場合は MODEL-GAP となり、モデルが弱すぎることを示す。 |
| FINDING | 設計上の破綻。反例の手順を表示する。 |
| MODEL-GAP / VACUOUS | モデル側の問題。結果を信用してはならない。 |

## M10 の結果（2026-10-27）

メッセージの形式 v6（端末ごとの連番、受け取った他端末の最新イベント、編集が置き換える版）の追加にあわせて作りました。初回の検査で FINDING が4件見つかり、いずれも実装を直しました：表示されていない編集に付いた注記が失われる（MO-drop、MO-order）、署名のないイベントが巨大な番号を名乗ると以後の欠落が隠れる（MO-forged-number）、記憶したキーの比較が前方一致だった（MO-split-remembered）。修正後は PASS 16、LIMIT 5、FINDING 0 です。LIMIT は、誰も後から参照しない端末の最新イベントの抜き取り（MO-tail）、最新ページだけ・フォーラムでの欠落（MO-suffix、MO-forum、MO-rollback-page）、拒否したと偽って同じ番号のイベントを2つ署名させた分岐（MO-split）です。対照実験では、ヘッドを1件だけ名乗る第1段階のクライアントで MO-order-hidden が、v6 以前のクライアントで MO-order と MO-drop が破綻することを確認しています。M9 は v6 でもすべて成立し、v5 で LIMIT だった MI-latest は v6 では成立します。

## 旧版（model.py）からの変更点

`model.py` は残してあります。次の検査は、構成上失敗しえないため、新しいモデルで置き換えました。

- M4.3：`P ∧ ¬P` を充足判定しており、常に UNSAT になる。
- M4.1 / M4.2：Z3 のデータ型が単射であることを確かめているだけで、監査の設計（鍵を持つ攻撃者、チェックポイントの巻き戻し）を表していない。
- M3.1：`stay` 遷移の定義に性質そのものが含まれている。また、未承認の端末でもセッションは実在するため、性質自体が実装と異なる。
- M2：pending と active を 1 つの状態変数で表しており、pending 中も active の鍵が存在すること（提案時に書き込みが止まる点も含む）を表せない。abort 後の active 名簿が未拘束になっている。

## M3 の書き換え（2026-10-07、継続 MLS グループ）

# formal-model — Alparts 設計検証モデル

Alparts のセキュリティ設計を、実装から写し取った規則で検証するモデルです。本番コードとは分離されており、実システムには接続しません（M1c だけは、実装の純粋関数をローカルで呼び出します）。

## 実行

```bash
pip install z3-solver          # M1 のみ使用
python3 run.py                 # 全モデル（M3 は数分、メモリ最大約 9 GB）
python3 run.py M1c M1 M2 M4 M5 # M3 以外（数分以内）
```

M1c は Node 24 と `pnpm install` 済みのリポジトリが必要です（`packages/server` の tsx を使用）。

## 判定の読み方

| 判定 | 意味 |
| --- | --- |
| PASS | 設計上の性質が成り立つ（HOLDS）。または、安全機構を外した弱化モデルで実際に破綻する（CONTROL）。後者は、対応する HOLDS 検査が空振りでないことの確認。 |
| LIMIT | 文書化済みの限界に、モデルが実際に到達する。到達できない場合は MODEL-GAP となり、モデルが弱すぎることを示す。 |
| FINDING | 設計上の破綻。反例の手順を表示する。 |
| MODEL-GAP / VACUOUS | モデル側の問題。結果を信用してはならない。 |

## モデル

| ID | 対象 | 手法 | 規模 |
| --- | --- | --- | --- |
| M1c | Python の評価関数と実装（`getChannelAuthorizationFromSnapshot` / `captureChannelViewersFromSnapshot`）の一致 | ランダム入力による差分テスト | 400 ワークスペース、約 2,000 マスク。allow 優先の変異体を検出できることも確認 |
| M1 | 認可の評価規則（複数ロール、ロール別のカテゴリ/チャンネル上書き、owner、非公開、音声） | Z3（全入力） | 3 ロール × 32 bit |
| M2 | ロール階層（作成・更新・削除・付与・剥奪・上書き・追放） | 状態の全探索 | 深さ 2 で約 13.7 万状態。付与経路は深さ 3 で約 16 万状態 |
| M3 | チャンネル鍵エポック（提案・受領・有効化・取得・移行済み旧エポックへの追加・送信・権限変更・端末の承認/失効・履歴復元・fresh start） | 状態の全探索と到達可能性の不動点 | 約 86 万状態 |
| M4 | 端末・承認・セッション（パスキーの 10 分制限、TOFU、復旧コード、失効、停止） | 攻撃者能力 32 通りごとの全探索と仕様照合 | — |
| M5 | 監査チェーン・チェックポイント・witness | 攻撃者能力 × 改ざん手段の全列挙 | — |

前提（全モデル共通）：署名・HMAC・AEAD は安全、トランザクションは直列化される（実装は advisory lock とワークスペースロックで直列化）。M3 の既定はサーバーが正直な場合で、不正なサーバーは別の変種で扱う。

## 旧版（model.py）からの変更点

`model.py` は残してあります。次の検査は、構成上失敗しえないため、新しいモデルで置き換えました。

- M4.3：`P ∧ ¬P` を充足判定しており、常に UNSAT になる。
- M4.1 / M4.2：Z3 のデータ型が単射であることを確かめているだけで、監査の設計（鍵を持つ攻撃者、チェックポイントの巻き戻し）を表していない。
- M3.1：`stay` 遷移の定義に性質そのものが含まれている。また、未承認の端末でもセッションは実在するため、性質自体が実装と異なる。
- M2：pending と active を 1 つの状態変数で表しており、pending 中も active の鍵が存在すること（提案時に書き込みが止まる点も含む）を表せない。abort 後の active 名簿が未拘束になっている。

## 結果（2026-09-29、修正後）

PASS 37、LIMIT 9、AU4b の FINDING 1 件（リスク受容、RISK_REGISTER R-047）。MODEL-GAP と VACUOUS は 0 件。

| 検査 | 初回の結果 | 対応後 |
| --- | --- | --- |
| M2 H2b / H2c | 下位のメンバーでも、共有ロールへの deny 上書きや deny 付きロールの付与で、上位メンバーの権限・表示を奪えた | `assertNoSuperiorAccessLoss` で拒否。非公開チャンネルからのメンバー削除にも同じ制限を追加。PASS。ガードを外した対照実験（H2b-ctl / H2d-ctl）では再び破綻する |
| M3 KL-orphan | 鍵を持つ端末も管理者も残っていないチャンネルが、自力で復旧できなかった | その状態に限り、管理者でない閲覧者も fresh start できる。そのとき管理者へ通知する。PASS。機密性（KC）も引き続き PASS |
| M5 AU4b | 巻き戻し検知が再起動で消える | 仕様として受け入れ、witness の必須化を推奨（FINDING のまま） |

M2 のガードは、検査する性質と同じ条件を実装で強制するものです。そのため M2 の PASS は「ガードを入れても H1 / H3 が壊れないこと」を示すもので、実装がその操作を実際に拒否することは結合テストで確認しています。

LIMIT は、TOFU（D3）、確認コードを見ずに承認した場合（D4）、応答しない端末によるエポック停止（F-KEY-007）、不正なサーバーによる名簿改ざん（F-E2E-001）、監査の未チェックポイント行・未 witness 区間（AU-L1〜L3）、評価の非単調性（A7 / A8）。

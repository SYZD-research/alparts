# formal-model — Alparts 設計検証モデル

Alparts のセキュリティ設計を、実装から写し取った規則で検証するモデルです。保証の対象は、各モデルに含めた状態と遷移の範囲に限られます。

実装照合で見つけた不一致を修正し、モデルと実サービスの回帰テストを追加しました。最新の結果は [アーキテクチャ変更後の再検証（2026-10-09）](./REVERIFICATION.ja.md)、それ以前は [修正・再検証記録](./REMEDIATION.ja.md) と修正前の反例の [実装照合記録](./IMPLEMENTATION_AUDIT.ja.md) にあります。モデル内のPASSを実装全体の保証に拡張することはできません。

既定の `run.py` はデータベースに接続しません。M1c / M2c / M5v / M6e / M8b / M9 は実装のコードをローカルで実行します。別途 `conformance/service-audit.mts` は、明示的に指定したテスト環境内に新規データベースを作って実サービスを検査します。

## 実行

```bash
pip install z3-solver          # M1 のみ使用
python3 formal-model/run.py                 # リポジトリルートから。M3は約6分・最大約0.9GB、M8は約11分
python3 formal-model/run.py M1c M1 M2 M2c M3r M4 M4s M5 M5v M6 M7 M9 # M3とM8以外（約5分）
python3 -m unittest discover -s formal-model -p 'test_*.py' -v # 検証器の負の検査
```

M1c / M2c / M5v / M6e / M8 / M9 は Node >=24.8 と `pnpm install`・sharedのビルド済みのリポジトリが必要です（`packages/server` の tsx ローダーを使用）。環境不足・出力欠落・判定不能はMODEL-GAPとなり、成功扱いにはしません。

## 判定の読み方

| 判定 | 意味 |
| --- | --- |
| PASS | 対象モデルの範囲で性質が成り立つ（HOLDS）。または、安全機構を外した弱化モデルで実際に破綻する（CONTROL）。後者は、対応する HOLDS 検査が空振りでないことの確認。 |
| LIMIT | 文書化済みの限界に、モデルが実際に到達する。到達できない場合は MODEL-GAP となり、モデルが弱すぎることを示す。 |
| FINDING | 設計上の破綻。反例の手順を表示する。 |
| MODEL-GAP / VACUOUS | モデル側の問題。結果を信用してはならない。 |

## 旧版（model.py）からの変更点

`model.py` は残してあります。次の検査は、構成上失敗しえないため、新しいモデルで置き換えました。

- M4.3：`P ∧ ¬P` を充足判定しており、常に UNSAT になる。
- M4.1 / M4.2：Z3 のデータ型が単射であることを確かめているだけで、監査の設計（鍵を持つ攻撃者、チェックポイントの巻き戻し）を表していない。
- M3.1：`stay` 遷移の定義に性質そのものが含まれている。また、未承認の端末でもセッションは実在するため、性質自体が実装と異なる。
- M2：pending と active を 1 つの状態変数で表しており、pending 中も active の鍵が存在すること（提案時に書き込みが止まる点も含む）を表せない。abort 後の active 名簿が未拘束になっている。

## M3 の書き換え（2026-10-07、継続 MLS グループ）

全員の受領を待つエポック方式（v3）から、チャンネルごとに継続する MLS グループ（v4、[ADR 0012](../docs/adr/0012-continuous-mls-groups.md)）への移行に合わせて、M3 を書き換えました。モデルは `mls-group-rules.ts`・`mls-group.service.ts`・`mls-group-gate.ts` とクライアントの `mls-group.service.ts`（同期・参加・参加し直し・commit・fresh start・バックグラウンドのパッケージ公開）から規則を写しています。メッセージは状態に持たず、書き込みができるすべての状態で、その時点の鍵を導出できる端末（その版のメンバー。後から追いつく場合を含む）、保持している端末、利用者のバックアップから得られる端末を検査します。

探索は3通りです。Python 3.13、`python3 formal-model/run.py M3` で 379 秒、最大 898 MB。

| 探索 | 内容 | 状態数 |
| --- | --- | --- |
| main | X1・Y1・Z1、閲覧者の変更2回・端末の変更2回、Y1 はいつでも永久にオフラインになりうる、最大6版 | 2,672,946 |
| faults | 読めない commit / Welcome を1回（他の全端末が処理に失敗する）、閲覧者・端末の変更各1回、最大6版 | 2,458,694 |
| second-device | X の2台目 X2（承認待ち）と履歴復元、閲覧者の変更なし・端末の変更2回、最大5版 | 1,082,911 |

到達可能性（KL 系）は、さらに2版を作れる状態のすべてのオンラインの適格な端末について、権限・端末の変更や故障を含まない手順だけで、その端末が書ける状態に到達できるかを後ろ向きの不動点で調べます。オンラインの使えるメンバーが1台でもログを追える状態（KL）では fresh start を使わず、そうでない状態（KL-orphan）では使います。15分・30分・72時間の待機は fresh start の遷移にまとめています（応答時間の保証ではありません）。

結果は **PASS 15 / LIMIT 3 / FINDING 0 / MODEL-GAP 0 / VACUOUS 0** です。

書き換え中に KA の反例が見つかり、クライアントを修正しました。オフラインの間にグループが置き換えられ（fresh start）、バックグラウンド処理でパッケージを公開して新しいグループに追加された端末が、古いグループの読めない envelope に当たると、参加し直しを求めて自分を追加した Welcome を使わず、新しいグループの履歴を失っていました（他のメンバーが追加し直すまで書けず、誰もいなければ fresh start が必要）。現在のメンバー期間より前の版が読めない場合は、古いグループだけを終えて現在のメンバー期間に Welcome から参加するよう `syncLocked` を変更し、クライアントの単体テストを追加しました。修正前の動作は KA-rejoin-ctl として残しています。

M3 の LIMIT は KA-unjoined、KC-dev-restore、KC-server の3件です。旧 M3 の KL-lost（F-KEY-007）は解消し、KA-ctl（F-KEY-001）は v3 の受け渡し経路がなくなったため、ログの提供範囲の対照に置き換えました。モデル化していないもの：パッケージの有効期限、commit と参加し直しの回数制限、7日ごとの leaf 更新、添付ファイル、不正なサーバーに対するクライアントの矛盾検出。応答が失われた自分の commit の採用は、2026-10-09 に M3r で扱いました。

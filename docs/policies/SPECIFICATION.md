# 高保証コミュニケーション基盤 要件定義書

**文書版:** v0.3
**作成日:** 2026年8月12日
**状態:** 要件合意前ドラフト
**対象:** セキュリティ研究、バグバウンティ、脆弱性調整、インシデント対応、機密会議を行う組織
**サーバー対象OS:** Linux
**クライアント対象:** Windows、Linux、macOS、iOS、Android、Web

---

## 1. 文書の目的

本書は、Discordに近い操作性を持ちながら、未公開脆弱性、ゼロデイ、PoC、認証情報を含み得るインシデント情報などを安全に扱う、セルフホスト可能なコミュニケーション基盤の要件を定義する。

本書では、具体的なプログラミング言語、フレームワーク、データベース、暗号ライブラリを原則として確定しない。要件と実装方式を分離し、技術選定は別途アーキテクチャ設計および検証用プロトタイプによって決定する。

---

## 2. 要件の優先度

| 優先度        | 意味                         |
| ---------- | -------------------------- |
| **MUST**   | 正式運用開始までに必須                |
| **SHOULD** | 原則として実装する。未実装の場合は理由と代替策が必要 |
| **MAY**    | 将来拡張または環境依存の任意機能           |
| **OUT**    | 初期スコープ外                    |

---

## 3. 用語

| 用語                    | 定義                                           |
| --------------------- | -------------------------------------------- |
| **デプロイメント**           | 一組のアプリケーション、DB、ストレージ、暗号・認証ポリシーからなる運用単位       |
| **ワークスペース**           | Discordにおける「サーバー」に相当する、ユーザー向けの最上位コミュニケーション単位 |
| **カテゴリー**             | 複数のチャンネルを整理し、権限や通知設定を継承できる単位                 |
| **チャンネル**             | テキスト、アナウンス、音声、会議などのコミュニケーション単位               |
| **公開チャンネル**           | ワークスペース内で閲覧権限を持つユーザーが、個別参加操作なしで閲覧できるチャンネル    |
| **プライベートチャンネル**       | 明示的に追加されたメンバーだけが存在と内容を閲覧できるチャンネル             |
| **端末**                | ユーザーが利用する個別のブラウザー、デスクトップアプリ、モバイルアプリ          |
| **外部ユーザー**            | 組織外の研究者、ベンダー、顧客、協力者など、制限された権限を持つユーザー         |
| **Restrictedワークスペース** | ゼロデイやEmbargo情報など、通常より厳しいポリシーを必要とするワークスペース    |
| **E2EE**              | サーバーを含む中継システムが内容を復号できないエンドツーエンド暗号化           |

# 4. 製品の基本定義

## 4.1 製品目標

本製品は、次を同時に満たさなければならない。

1. **Discordに近い直感的なチャンネル型UX**
2. **メッセージ、添付ファイル、通話内容の高い機密性**
3. **日常操作で暗号や鍵を意識させない設計**
4. **単一Linuxサーバーからクラスタ構成まで移行可能な運用性**
5. **少ないCPU・メモリでの安定動作**
6. **障害発生時の自動復旧とデータ耐久性**
7. **クライアント、サーバー、プロトコルの監査可能性**
8. **インターネットへ接続しない閉域環境でも利用可能な自己完結性**
9. **本番環境の管理者であっても、権限なく会話本文を読めない構造**
10. **安全性を理由にユーザーが別のチャットサービスへ迂回しない実用性**

## 4.2 成功条件

正式運用開始時には、少なくとも以下が成立していなければならない。

* 一般ユーザーが暗号鍵を操作せずに通常のチャットを利用できる。
* 公開チャンネルを閲覧するための「参加」操作が不要である。
* カテゴリー、チャンネル、未読、スレッドを高速に移動できる。
* 新端末でも安全な復旧手続きを経て過去履歴と検索機能を利用できる。
* サーバー、DB、オブジェクトストレージ、バックアップの取得だけではメッセージ本文を復号できない。
* アプリケーションノード停止後に自動復旧できる。
* 単一ノードから複数ノードへ、ユーザーIDやメッセージIDを変更せず移行できる。
* 正式配布物の改ざんをクライアントおよび管理者が検出できる。
* ログ、メトリクス、クラッシュダンプに会話本文や秘密情報を含めない。

# 5. 設計原則

## 5.1 セキュリティを通常操作へ露出させない

ユーザーは、通常のメッセージ送信、検索、チャンネル移動、リアクション、通話参加において、暗号方式、鍵、暗号グループ、鍵エポックなどを選択してはならない。

暗号化、鍵配布、メンバー変更時の再鍵生成、端末間同期はバックグラウンドで自動処理する。

## 5.2 確認操作は信頼境界が変化する場合に限定する

追加確認やステップアップ認証は、主に次の場合に要求する。

* 新しい端末の登録
* 外部ユーザーの招待
* Restrictedワークスペースへのメンバー追加
* Botまたは外部連携の追加
* 大量データのエクスポート
* 復旧鍵または組織復旧機能の利用
* Ownerや特権管理者の変更
* 暗号・認証・監査ポリシーの弱体化
* バックアップの削除
* クライアント署名鍵の変更

日常的な投稿やチャンネル管理に、過剰な承認フローを設けてはならない。

## 5.3 ネットワーク位置を認証の代替にしない

Tailscale、WireGuard、Cloudflare Accessなどの閉域化やZTNAは防御層として利用できるが、VPN内、社内IP、特定ネットワークからの接続だけを理由にユーザーを信頼してはならない。

アプリケーション認証、端末認証、認可、監査はネットワーク制御と独立して維持する。これはネットワーク位置だけに暗黙の信頼を置かないゼロトラストの原則に対応する。

## 5.4 セキュリティ境界はワークスペース単位とする

通常チャンネルと最高機密チャンネルで毎回異なる操作を要求すると、ユーザーの誤操作と迂回利用を招く。

したがって、強いセキュリティポリシーは原則としてチャンネル単位ではなくワークスペース単位で適用する。

特に高い隔離が必要な場合は、Restrictedワークスペースを別デプロイメント、別DB、別ネットワーク、別バックアップ資格情報で運用できなければならない。

## 5.5 「バグがない」を検証可能な条件へ置き換える

完全なバグゼロを要件とはしない。代わりに以下を要求する。

* 既知で悪用可能なCritical脆弱性を残したまま正式リリースしない。
* 暗号、認証、認可、復旧、アップデート機構を重点レビュー対象とする。
* セキュリティ不変条件を自動テストする。
* 問題発見後に失効、更新、ロールバックできる。
* リリースごとにSBOM、署名、ビルドプロベナンスを提供する。
* 独立した外部セキュリティレビューを実施する。

* 受信済みデータの完全な遠隔消去
* サーバーに対する完全なメタデータ秘匿

# 7. セキュリティプロファイル

プロファイル差は、通常のメッセージ操作ではなく、外部共有、履歴、復旧、Web利用、連携などの信頼境界に限定する。

| 項目            | Standard Secure | Restricted / Embargoed |
| ------------- | --------------- | ---------------------- |
| メッセージ・添付E2EE  | 必須              | 必須                     |
| Webクライアント     | 許可              | 管理ポリシーで禁止可能            |
| 新メンバーの過去履歴    | 自動共有            | 参加後のみを既定にできる           |
| 新端末の履歴復旧      | 暗号化バックアップから可能   | 既存端末承認または閾値復旧          |
| 暗号化検索インデックス同期 | 既定で有効           | 無効化可能                  |
| 外部ユーザー        | 明示招待            | 追加承認を要求                |
| Bot・Webhook   | 明示的に許可          | 既定で禁止                  |
| Push通知本文      | ユーザー設定          | 既定で非表示                 |
| データエクスポート     | 監査対象            | 二者承認可能                 |
| 管理者による復旧      | 明示ポリシー時のみ       | 閾値型または無効               |
| 推奨配置          | 通常デプロイメント       | 専用デプロイメント              |

プロファイルを変更してセキュリティを弱める場合は、影響を受ける全ユーザーへの通知、監査記録、必要に応じた再鍵生成を必須とする。

サーバー管理者がユーザーへ通知せず、復旧受信者、監査対象外Bot、復号可能な端末を追加できてはならない。

## 10.1 暗号化対象

## 11.2 デスクトップ

デスクトップクライアントは、Web技術を利用したシェルを採用してもよい。ただし、フレームワーク名ではなく以下の性質を満たさなければならない。

* WebViewからネイティブ機能へのIPCを最小権限化する。
* 任意シェル実行機能を通常ビルドへ含めない。
* ファイルアクセス範囲を限定する。
* リモートJavaScriptをアプリ本体へ読み込まない。
* UI資産を署名済み配布物へ同梱する。
* ウィンドウまたはWebViewごとに権限を制限する。
* アップデートを署名検証する。
* 外部URLをアプリ内の特権WebViewで直接開かない。

Tauri 2は候補の一つであり、WebViewごとのCapability制御とアップデート機構を提供しているが、採用自体を本要件では固定しない。

## 13.2 添付ストレージ

* オブジェクトストレージには暗号文だけを保存する。
* ストレージアクセスURLは短時間かつ対象オブジェクトへ限定する。
* オブジェクトIDから元ファイル名やチャンネル名を推測できないようにする。
* 未完了アップロードを期限後に回収する。
* ストレージ容量制限をユーザー、ワークスペース、チャンネル単位に設定できる。
* 削除済みオブジェクトの回収処理を監視する。

* 時刻同期状態を監視する。
* アラートには機密データを含めない。
* 可観測性基盤が停止してもメッセージ処理を全面停止させない。
* 可観測性基盤への送信は無効化可能とし、外部SaaSを必須にしない。

# 23. セキュリティ受入基準

正式運用前に、少なくとも以下を実証する。

1. **DB・ストレージ窃取**
   DB、オブジェクトストレージ、バックアップだけを取得しても、メッセージと添付を復号できない。

2. **管理者分離**
   サーバー管理者がチャンネルメンバーでない場合、会話本文を復号できない。

3. **端末鍵置換**
   サーバーが不正な端末鍵を提示した場合、既存クライアントがSplit Viewまたは整合性異常を検出する。

4. **端末追加通知**
   新端末登録が既存端末へ通知される。

5. **端末失効**
   失効端末が以降のメッセージを復号できない。

6. **メンバー削除**
   削除済みメンバーへ新しいメッセージ鍵が配布されない。

7. **Restricted履歴**
   「参加後のみ」設定の新規メンバーが過去履歴を復号できない。

8. **改ざん検出**
   メッセージ、添付、権限、メンバーシップイベントの改変が検出される。

9. **重複排除**
   同じ送信要求を複数回送信しても、UI上のメッセージが重複しない。

10. **ログ漏洩**
    ログ、トレース、メトリクス、クラッシュダンプに平文や秘密情報が含まれない。

11. **悪性添付**
    HTML、SVG、実行ファイル、ZIP爆弾、壊れた画像が自動実行・無制限展開されない。

12. **アップデート改ざん**
    改ざんされたサーバーまたはクライアント更新が拒否される。

13. **Web制限**
    RestrictedでWeb利用を禁止した場合、Webクライアントから内容へアクセスできない。

14. **復旧透明性**
    組織支援型復旧が有効な場合、ユーザーがその状態を確認できる。

15. **秘密裏の復旧追加防止**
    管理者が通知や監査なしに新しい復旧受信者を追加できない。

16. **Bot可視性**
    Botが参加するチャンネルで、全ユーザーがBotの存在を確認できる。

17. **通話E2EE**
    SFUおよびTURNの保存データやメモリから通話本文を復元できない。

18. **Push秘匿**
    Push事業者へ渡るデータに平文メッセージが含まれない。

# 24. 可用性・運用受入基準

1. 稼働中のアプリケーションノードを強制終了しても、ACK済みメッセージが失われない。
2. HA構成では、ノード停止後60秒以内に接続が復旧する。
3. クライアントが最後の同期位置から再開する。
4. DBフェイルオーバー後も、権限、メンバーシップ、順序、重複排除が維持される。
5. メッセージブローカーを停止しても、正式データが失われない。
6. バックアップを新しい隔離環境へ復元できる。
7. 復元後のメッセージ、添付、権限、監査ログの整合性検査に合格する。
8. 単一ノード環境を複数ノード環境へ移行できる。
9. 移行前後でユーザー、チャンネル、メッセージIDが維持される。
10. 不可逆マイグレーション前にバックアップ未取得の場合、更新処理が停止する。
11. ローリング更新中にサービスが継続する。
12. 更新失敗後に安全なロールバックまたはロールフォワードができる。
13. インターネットへのアウトバウンド接続を遮断しても、コアメッセージングが動作する。
14. Small負荷の3倍で短時間ピーク試験を実施し、データ損失や無制限メモリ増加が起きない。
15. 72時間以上のソークテストで、継続的なメモリ増加や接続リークが発生しない。

# 28. 最終原則

本製品の中心要件は、次の一文に集約される。

> **通常時はDiscordと同等以上に速く自然に使え、信頼境界が変わる瞬間だけ確実なセキュリティ確認を行い、サーバーや運用者が侵害されても会話本文の機密性を可能な限り維持できること。**

セキュリティ機能を増やすこと自体を目的としてはならない。

ユーザーが面倒さを避けるためにDiscord、メール、個人アカウント、未管理ストレージへ機密情報を移すなら、そのセキュリティ設計は失敗である。したがって、検索、履歴復旧、Web、モバイル、通知、通話、チャンネル移動といった実務上の中心機能は、暗号化と同じレベルの必須要件として扱う。

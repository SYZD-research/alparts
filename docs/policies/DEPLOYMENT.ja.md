## 対応する構成

| 構成 | 状態 | 用途 |
| --- | --- | --- |
| 開発 | 実装済み | 使い捨てのDockerのPostgreSQL・SeaweedFSを使う、ループバック限定のローカル開発 |
| 単一ホストでの本番の試験運用 | テンプレートを実装済み。デプロイ時の受け入れ確認が必要 | systemdまたは強化したComposeで動かす1つのNodeプロセスと、永続的な外部またはローカルのPostgreSQLとS3互換ストレージ |

| 複数リージョンの本番 | 未対応 | 設計上の目標のみ。リーダーの排他制御、競合、フェイルオーバーのモデルがありません |
| ネットワーク隔離環境・エッジ機器 | 単一ホストの範囲で条件付きで対応 | 正確なパッケージ・イメージ・ツールを事前に用意し、ローカルの永続的な依存サービス、時刻、証明書、オフラインでのバックアップの書き出しを用意します |

保証することと保証しないことは、[機能レベル](../deployment/CAPABILITY_LEVELS.md)（英語）を参照してください。

## 設定の仕組み

設定の取得元は2つで、次の順に適用します。

1. 秘密ではない、範囲が限られた設定の安全な組み込みの既定値
2. 明示的な環境変数（秘密情報には、それと排他的な `NAME_FILE` の形式）

汎用の設定ファイル、外部のシークレット取得APIとの連携、実行時に上書きする仕組みはありません。Dockerのsecretとsystemdのcredentialは、`NAME_FILE` に渡すための手段です。`NAME` と `NAME_FILE` の両方を指定するとエラーになります。型や範囲が不正な値、弱い必須の秘密情報、安全でない待ち受けアドレスやオリジン、本番での監査の外部証跡の欠落、ループバック以外の安全でない依存サービスがあると、起動を中止します。

`S3_ENDPOINT` はホスト名またはIPアドレスだけを指定します（スキーム、ポート、パスは含めず、`S3_PORT` と `S3_USE_SSL` を使います）。`S3_REGION`、`S3_BUCKET`、`AUDIT_HEAD_BUCKET` は、有効なリージョン名と、DNSで使えるバケット名でなければなりません。それ以外の値では起動を止めます。暗号化されないオブジェクトストレージは、ループバックのアドレスを直接指定した場合にだけ許可します。S3クライアントは、環境にある `AWS_USE_FIPS_ENDPOINT` と `AWS_USE_DUALSTACK_ENDPOINT` の切り替えを無視します。

登録時には、登録するアドレスに確認コードをメールで送ります。`SMTP_HOST`、`SMTP_FROM`、必要に応じて `SMTP_USER` と `SMTP_PASSWORD_FILE` を設定し、最初からTLSで接続する場合は `SMTP_SECURE=true` を設定します。それ以外の場合、本番ではSTARTTLSが必須です。SMTPがない場合、本番では既存のアカウントの利用は続けられますが、`EMAIL_VERIFICATION=disabled` で確認を明示的に無効にしない限り、新規登録を拒否し、起動時に `registration.unavailable` をログに記録します。メールは、利用者がアプリで選んだ言語に合わせて日本語または英語で送ります。設定は不要です。

サービスは、利用できる機能を暗黙に自動判別しません。運用者が、確認済みの構成を明示的に選びます。Kubernetes、KMS、高可用性の仕組みがないことを理由に、認証、認可、TLSの要件、監査の完全性が無効になることはありません。

## 共通の事前確認

本番での起動や更新の前に、毎回次を行います。

1. 正確なGitのリビジョン、変更できないOCIのダイジェスト、Node・pnpmのバージョン、移行の一式を特定します。
2. 扱うデータの区分に照らして、[制限](./LIMITATIONS.md)と[未解決のリスク](../RISK_REGISTER.md)（英語）を確認します。
3. リポジトリの外で一意の秘密情報を生成し、保護されたファイルやシークレット管理のマウントから渡します。
4. 専用のPostgreSQL 16のデータベースと `public` スキーマ、PostgreSQL・オブジェクトストアの接続先の身元、TLSの信頼設定、最小権限のロール、ストレージの永続性と容量を確認します。
5. ビルド、lint、型チェック、テスト、秘密情報と依存関係のスキャンを行い、実際に使うイメージをビルドします。
6. すべての移行を新しい使い捨てのデータベースに適用し、PostgreSQLとオブジェクトストアを使う結合テストを実行します。
7. 既存のデプロイでは、書き込みを止めて受け付けを停止し、移行前の暗号化されたバックアップを作成して、独立して復元・検証します。
8. アプリケーションを停止した状態で、別のデプロイ用IDで移行を適用します。
9. データベースに適用済みの移行のタイムスタンプとハッシュ、範囲を限ったPostgreSQL 16のカタログのフィンガープリントが、実行するイメージと完全に一致することを確認します。
10. 監査チェックポイントの初期化は、初回のデプロイでだけ行い、その後は毎回の起動で必須にします。
11. アプリのプロセスを1つ起動し、startupとreadiness、認証付きの合成的な読み書きで確認したうえで、エラーと負荷の状況を監視します。
12. 1つ前の変更できないイメージを残し、前向きの修正か復元かという巻き戻しの判断を文書にしておきます。

readinessを成功させるためだけに、欠けた監査チェックポイントを再び初期化しないでください。検証済みのバックアップと、別途練習した復旧手順なしに、破壊的な移行を適用しないでください。

## オブジェクトストレージ

添付ファイル、プロフィール画像、永続的な監査のheadは、S3互換のオブジェクトストアに保存します。推奨するストアは [SeaweedFS](https://github.com/seaweedfs/seaweedfs)（Apache-2.0）です。開発とCIでは、ダイジェストで固定したSeaweedFS 4.47を動かします（`docker-compose.yml`、`scripts/ci/start-object-storage.sh`）。サーバーは、どのストアにも、AWS SDK for JavaScript v3を使い、パス形式のリクエストで接続します。

| 設定 | 意味 |
|---|---|
| `S3_ENDPOINT`、`S3_PORT`、`S3_USE_SSL` | 接続先のホスト、ポート、TLS（本番では、承認したループバックの接続先を除き、TLSが必須） |
| `S3_ACCESS_KEY`、`S3_SECRET_KEY`（または `*_FILE`） | アプリケーション自身のID |
| `S3_BUCKET`、`AUDIT_HEAD_BUCKET` | オブジェクトのバケットと、別の監査head用のバケット（既定は `${S3_BUCKET}-audit`） |
| `S3_REGION` | 署名に使うリージョン（既定は `us-east-1`） |
| `S3_REQUEST_TIMEOUT_MS` | リクエストごとの絶対的な期限（既定は10秒、最大60秒） |

以前の `MINIO_*` の名前は、起動時とバックアップのスクリプトで拒否し、変更すべき名前を一覧で表示します。

本番でSeaweedFSを使う場合:

- 固定したイメージを、専用の永続的なボリュームで動かします。容量を計画し、必要に応じてSeaweedFSのレプリケーションを使います。1つのボリュームでは冗長化されません。復旧には暗号化されたバックアップを使います。
- アプリケーションのホストに公開するのは、TLS経由のS3 APIだけにします（SeaweedFSの `-s3.port.https` と `-s3.cert.file`・`-s3.key.file`、または同じホスト上のTLSプロキシ）。テレメトリーを無効にし（`-master.telemetry=false`）、管理画面、master、volume、filerのポートをネットワークに出さないでください。
- `-s3.config` ファイルでIDを定義します。バケットを作成し、アプリケーションには決して渡さない管理者、`S3_BUCKET` と `AUDIT_HEAD_BUCKET` に `Read`・`Write`・`List` を持つアプリケーション、`S3_BUCKET` にだけ `Read` と `List` を持つバックアップ用のID、使い捨ての検証用バケットごとの別のIDです。SeaweedFSはバケット単位で権限を与え、`Write` には削除も含まれるため、アプリケーションは監査のheadも削除できます。[運用ガイド](../OPERATIONS.ja.md)で説明しているとおり、ストアの管理者とアプリケーションのホストは、headを巻き戻せるものとして扱ってください。
- 初回の起動前に、両方のバケットを作成します（例: `-bucket=alparts,alparts-audit`）。アプリケーションは、通常の起動時に監査head用のバケットを作成しません。

### 既存のMinIOの環境から移行する

1. アプリケーションの書き込みを止め、移行元のリリースのスクリプトでバックアップを取り、復元して検証します。
2. SeaweedFSに、両方のバケットと上記のIDを作成します。
3. アプリケーションを停止したまま、`S3_BUCKET` と監査head用のバケットのすべてのオブジェクトを、キーを保ったままコピーし（例: `rclone copy old:alparts new:alparts` と、`alparts-audit` も同様に）、両方のオブジェクト数とサイズを比較します。監査のheadがないと、意図して初期化し直すまでサーバーは起動しないため、作り直すのではなくコピーしてください。
4. 環境変数、Composeのsecret（`s3_access_key`、`s3_secret_key`）、systemdのcredentialにある `MINIO_*` の設定をすべて `S3_*` に名前を変え、`S3_ENDPOINT` をSeaweedFSに向けます。バックアップのジョブは、`S3_URL`、`S3_ACCESS_KEY`、`S3_SECRET_KEY`、`S3_BUCKET` と、`mc` の代わりに `rclone` を使います。
5. アプリケーションを起動し、書き込みを再開する前に、readinessと添付ファイルのダウンロードを確認します。

## 開発

```bash
./dev.sh
```

`docker-compose.yml` は依存サービス専用で、開発専用です。ポートはループバックに限って公開し、生成した `.env` の秘密情報はローカルでモード `0600` にします。認証情報が一致しない場合も、ボリュームを自動で削除しません。依存サービスは `./dev.sh down` で停止します。

開発用の認証やTLSの設定を、本番に流用しないでください。明示的な初期招待用の秘密情報を設定しない限り、公開の登録は無効のままです。

## systemdを使った単一ホストでの本番

必要なもの:

- Linuxのホスト、Node.js 24以降、`/opt/alparts` に置いたビルド済みのリポジトリ
- HTTPSだけを公開し、`127.0.0.1:3000` に転送するリバースプロキシ
- サービス専用の、永続的なPostgreSQLとS3互換のオブジェクトストア
- `/etc/alparts/credentials` に置いた保護された認証情報と、`/etc/alparts/alparts.env` に置いた秘密ではないポリシー
- 永続的な `/var/lib/alparts-audit`（できれば権限を分けたマウント上）
- 暗号化した `/var/lib/alparts-backups` と、独立した別ホストのストレージへの転送
- ディスク、証明書、プロセス、バックアップ、合成的なサービスの外部監視

環境に応じて実行ファイルやパスを変更してから、ユニットをインストールして検証します。

```bash
sudo install -m 0644 deploy/alparts.service /etc/systemd/system/alparts.service
sudo install -m 0644 deploy/alparts-backup.service /etc/systemd/system/alparts-backup.service
sudo install -m 0644 deploy/alparts-backup.timer /etc/systemd/system/alparts-backup.timer
sudo systemd-analyze verify /etc/systemd/system/alparts.service \
  /etc/systemd/system/alparts-backup.service /etc/systemd/system/alparts-backup.timer
sudo systemctl daemon-reload
```

アプリのユニットの例では、動的に割り当てるroot以外のUID、読み取り専用のファイルシステムの保護、capabilityなし、メモリー・タスク・ファイル記述子の上限、再起動の間隔の延長、ループバックでの待ち受けを使います。例にある、安全でない依存サービスを明示的に許可する設定は、PostgreSQLとオブジェクトストアの接続先が本当にループバックかローカルのUNIXソケットの場合にだけ有効です。リモートの接続先では、検証済みのTLSを使い、その許可の設定を削除してください。

アプリを停止した状態で、本番の認証情報を使って、最初の監査チェックポイントを作成します。

```bash
pnpm --filter @alparts/server audit:checkpoint:init
```

その後、起動して確認します。

```bash
sudo systemctl enable --now alparts.service
curl --fail http://127.0.0.1:3000/health/startup
curl --fail http://127.0.0.1:3000/health/ready
sudo systemctl enable --now alparts-backup.timer
```

バックアップでは、PostgreSQLとオブジェクトストアの内容をそろえるため、意図的にアプリケーションを停止します。ラッパーは、重複をロックで防ぎ、すでに停止しているサービスには手を付けず、trapで再起動し、承認がある場合にだけ、暗号化された成果物の正確な名前のものを削除します。バックアップのユニットから `Requires=alparts.service` を外しているのは意図的です。アプリを止めたときに、書き込み停止の時間を始めたバックアップのジョブまで止まってはいけないためです。

## Composeを使った単一ホストでの本番

`compose.production.yml` に含めているのはアプリケーションだけです。PostgreSQLとオブジェクトストレージは明示的な依存サービスとして扱い、Composeのプロジェクトを高可用性の構成に見せかけることなく、永続的なローカルのサービスにも、マネージドの接続先にもできるようにしています。

このプロファイルには、変更できないイメージのタグ、正確なHTTPSのオリジン、依存サービスの接続先、アプリケーションの6つの秘密情報のファイルと、範囲を分けた7つ目の、移行用のデータベースの秘密情報が必要です。`TRUSTED_PROXIES` には、コンテナーから見たリバースプロキシのアドレス（例: ブリッジのゲートウェイ）を設定してください。HTTPとSocket.IOの制限はクライアントのアドレスごと（IPv6は/64ごと）に数えるため、この設定がないと、すべてのクライアントがプロキシの1つの枠を共有することになります。この設定が空のまま転送されたリクエストを受け取ると、サーバーは `network.forwarded_without_trusted_proxy` を一度だけログに記録します。ホスト側のポートはループバックで公開し、読み取り専用のルートファイルシステム、tmpfs、Linuxのcapabilityなし、`no-new-privileges`、PID・メモリー・CPUの上限、root以外のイメージのユーザー、永続的な監査チェックポイントのボリューム、正常な停止、再起動のポリシー、readinessのヘルスチェックを使います。

起動前に検証します。

```bash
docker compose -f compose.production.yml config --quiet
docker compose -f compose.production.yml build --pull app
docker compose -f compose.production.yml --profile operations run --rm --no-deps migrator
# First deployment only; never use this to bypass an unexplained missing witness.
docker compose -f compose.production.yml run --rm --no-deps app \
  node packages/server/dist/scripts/initialize-audit-checkpoint.js
docker compose -f compose.production.yml up --detach --wait
```

初期化や起動の前に、`AUDIT_HEAD_BUCKET` に別のオブジェクトストアのバケットを、`AUDIT_HEAD_OBJECT_KEY` に変わらないデプロイの識別子を設定します。アプリケーションには、そのheadの取得と保存の権限を与えます。データベースやチェックポイントの修復、データの復元に使うIDに、headを上書きさせてはいけません。既存のチェックポイントでは、独立して検証した後に、[運用ガイド](../OPERATIONS.ja.md)で説明している、サーバーを停止した状態での `audit:head:init` による移行が必要です。headの識別子を作り直したり、通常の復元の一部としてこのバケットを過去の状態に戻したりしないでください。

イメージには、ビルドに使った、順序の決まった移行の一式がそのまま含まれています。データベース専用の実行時の移行ツールが受け取るのは、別の移行用のURLと、範囲を限ったデータベースの設定だけです。待たないPostgreSQLのadvisory lockを使い、接続と文の期限を守り、別の移行ツールが動いていれば終了します。サーバーは、起動時とreadinessの確認時に、適用済みのすべての移行のタイムスタンプとSHA-256、範囲を限ったPostgreSQL 16の `public` カタログのフィンガープリントを、イメージが前提とする内容と比較します。空、古い、変更された、順序が入れ替わった、未知の新しいもの、継続的に改変されたスキーマは、安全側に失敗します。このため、Alparts専用の `public` スキーマが必要で、確認済みの互換性のための移行でフィンガープリントを更新するまで、別のメジャーバージョンのPostgreSQLは意図的に拒否します。既存のデプロイでは、このコマンドの前に、書き込みを止めたバックアップと隔離環境での復元の確認を完了する必要があります。チェックポイントの初期化は、初回のデプロイの後は省略してください。既存のチェックポイントが上書きされることはありません。

実際のリリースの仕組みでは、できたイメージをダイジェストで固定してデプロイしてください。このリポジトリは現在、ベースイメージのタグとCIのアクションを固定していますが、署名付きのリリースや証明（attestation）は公開していません。

## ローリング更新・カナリア・巻き戻しの方針

現在のアプリは2つの稼働中のレプリカを動かせないため、アプリケーションのローリング更新やカナリアリリースは使えません。単一ホストでの更新は、管理された停止 → バックアップと復元の確認 → 移行 → 起動 → ヘルスチェックと合成的な確認、の順で行います。練習には、2つ目の稼働中の書き込み元ではなく、別の隔離された環境を使ってください。

巻き戻しの選択肢:

- スキーマの後方互換性が保たれている場合は、停止して、1つ前の変更できないイメージを実行します。
- 前向きの移行によって古いバイナリとの互換性がなくなっている場合は、修正のための前向きの移行をデプロイするか、検証済みの移行前のバックアップを新しい空の環境に復元します。本番に対して、その場しのぎの巻き戻しの移行を実行しないでください。
- 失敗したデータベースや成果物は、調査のために保存しておきます。起動を成功させるためだけにデータを消去しないでください。

## クラスターと複数リージョンの目標

現在でも、1つのアプリのプロセスの背後で、外部のデータベースやオブジェクトストアの高可用性の仕組みは使えます。アプリのレプリカを複数動かすには、レート制限と受付枠の共有された状態、分散したSocket.IOのルーム、排他制御付きのアップロードの調整、認可の改訂の共有された無効化、永続的な複数書き込み元に対応した監査の外部証跡が必要です。これらを実装し、ネットワーク分断の試験を行うまでは、レプリカによって受付制御、ルーム、監査の動作が一貫しなくなる可能性があります。

複数リージョンでの運用には、さらに、宣言された一貫性のモデル、排他制御された単一の書き込みリーダーか競合の起きない領域の設計、レプリケーションの遅延時の動作、フェイルオーバーの権限、スプリットブレインの防止、時刻の前提、テスト済みのデータとクライアントの鍵の復旧手順が必要です。DNSやロードバランサーによるフェイルオーバーだけでは不十分です。

## ネットワーク隔離環境とエッジ

正確なOCIイメージまたはpnpmのストア、PostgreSQLとSeaweedFSのパッケージ、ルート証明書、`age`、`rclone`、PostgreSQLのツール、SBOM、チェックサム、運用者向けのドキュメントを事前に用意します。デプロイ中に、ネットワークに依存するパッケージのインストールを無効にします。信頼できるローカルの時刻源、オフラインでの証明書更新の計画、2人で扱うリムーバブルメディアへのバックアップの書き出し、テスト済みのクリーンな環境での復元を用意してください。ネットワークが隔離されているからといって、認証、TLS、監査を弱めないでください。

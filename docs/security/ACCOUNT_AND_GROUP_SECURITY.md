# Account, device, group and history security

Implementation: 2026-09-16; group protocol 4 (one continuing MLS group per channel, [ADR 0012](../adr/0012-continuous-mls-groups.md)): 2026-10-07. This document supersedes the earlier password-only/RSA-group descriptions and the per-epoch group protocol 3. It describes implemented controls and remaining assurance work, not production approval.

## Device approval and transparency

`devices.approved_at` separates possession of an account login from possession of an approved messaging device. A password-only session cannot approve itself, receive group secrets, or perform step-up operations until bound to an approved device. Existing identities still require their private signing key to bind another session. The active-device limit includes pending identities; revoking an identity also invalidates its sessions.

The first device signs a challenge. Additional registrations sign their own challenge but remain unapproved. Approval, revocation and recovery-policy changes bind the account, predecessor sequence/hash, target identity and approving device. Transactions append the event together with the state change. A PostgreSQL trigger refuses directory UPDATE/DELETE; this is defense in depth, not protection from a database superuser.

Clients verify a bounded suffix from their last encrypted local checkpoint. Reordered entries, substituted identity keys, invalid signatures, inconsistent old checkpoints and rollback fail closed. Every signed group commit carries the directory head of each member's account; clients refuse a head that moves back and verify every head that changed, providing in-band comparison. The account-security screen also lets users compare an earlier checkpoint from another device directly, outside the service. A split view that never meets another pinned view cannot be detected by a single client; first contact needs an external trust anchor for stronger assurance.

Historical verification evaluates approval/revocation at the referenced head. Revocation removes future eligibility without making previously received message signatures or archive keys invalid. Channel directory lookups include historical message, attachment and key-distribution signers.

## Group-key lifecycle

Since migration 0023 every channel has one continuing RFC 9420 group (group protocol 4). It replaces protocol 3, which built a new group for every key version and activated it only after every recipient device confirmed it. The fixed suite is `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.

Terms used below: an **eligible device** is an approved, non-revoked device of a user who currently sees the channel. A **member** is a device with a leaf in the current group. A **usable member** is an eligible member without an open rejoin request. A **group refresh** is an accepted genesis, a commit that removes a device, or an empty commit; the last two carry an UpdatePath (add-only commits never do).

1. **Packages.** Every eligible device publishes a one-time X25519/Ed25519 KeyPackage for each channel it sees, signed with its P-256 identity. The server checks the MLS signatures, suite, lifetime, credential identity (the device ID), the canonical encoding and the device signature. A package ID is accepted once (`PACKAGE_CONSUMED` on reuse), and none of a package's keys may repeat a key of another published package, a current leaf or a tree node the group already accepted (`PACKAGE_KEY_CONFLICT`). A package can be added while its start time is at least 10 minutes in the past and at least one hour of its seven-day lifetime remains. Clients reuse an unconsumed package for up to six days and publish packages for every channel they see when channel lists load and when the server reports work for them (`GET /mls/group/pending`), across all workspaces.
2. **Genesis.** The first eligible device creates the group with its own package and Adds for every other package it can verify against the device directory (`kind: 'create'`). The group ID binds the channel and the genesis version. Each version's 32-byte AES-256-GCM channel key comes from the MLS exporter (label `alparts-channel-epoch-v2`, context = group ID and version). A signed envelope (the committer device's P-256 signature) binds the version, the previous version and its transcript, group ID, epoch, the commit (always a PublicMessage), the Welcome, the added packages, the removed devices, the resulting roster with leaf indexes, the directory heads of every member's account and the key commitment. The transcript of a version is the SHA-256 of that envelope.
3. **Commits.** A usable member commits changes to the group: a Remove for every member that is no longer eligible (mandatory), Adds for pending packages it can verify (optional; never required for a commit to be accepted), a rejoin (remove and re-add the same device in one commit), or an empty commit that refreshes the group key. Add-only commits carry no UpdatePath. When a refresh is due and nobody leaves, the client commits the empty commit first and the additions next.
4. **Ordering and admission.** The server accepts exactly one commit per version: compare-and-swap on the version and on the previous version's transcript, under the key-protocol, workspace and channel locks, so a commit is ordered against role, membership and device changes. It checks the committer device, the envelope signature, that the committer is a usable member whose leaf sent the commit (for a genesis: an eligible device whose own package comes first), that Remove and Add proposals match `removed` and `added`, the roster arithmetic (new devices take the lowest free leaves), the Welcome's recipients, the UpdatePath leaf credential and signature key, current directory heads and that every added package equals its published row byte for byte. Answers that depend on state a client may have read earlier are 409; envelopes that are invalid in every state are 403. A commit retried with the same bytes gets the same answer (lost responses are safe). Add-only and empty commits are limited to 60 per channel per hour; empty commits are accepted only when a refresh is due. Commits that remove a device are never rate limited. The server cannot read the exporter secret or check path secrets.
5. **Accepted means active.** The accepted commit becomes the active version in the same transaction and the previous version is retired. There is no pending state, no acknowledgement and no abort, and versions are never reused. Audit records name the committer device, the transcript and the added and removed devices of every version.
6. **Catch-up and join.** Members process commits in version order from the commit log (at most 16 versions and about 4 MiB per page). Before a device advances it checks that each envelope chains to its last verified version, its signature, that directory heads never move back, the committer's membership and leaf, every added package, that the processed tree matches the signed roster, and the key commitment. A device added by a commit joins from that commit's Welcome and checks the roster at that commit's directory heads, so a member revoked later does not prevent the join. Each derived version key is saved, together with its recovery backup or a marker to retry the backup, before the advanced group state. Old epoch secrets are not kept in the saved group state.
7. **Writes.** A message, edit, delete or forum post must use exactly the active version and come from a current member device; an older version is refused with `KEY_VERSION_STALE` and the current version. Writes are refused (`KEY_ROTATION_REQUIRED`) only while the group still contains a device that is no longer eligible (revoked, unapproved, or its user no longer sees the channel), or while no group refresh has been accepted for 24 hours. Any one online usable member lifts either block with one commit; a usable member's client commits the removal or refresh before it seals a message, and background work on other online members' devices commits removals a few seconds after they are notified. Offline devices and devices waiting to be added never block writes. Attachment finalization keeps the version of its message while the uploader is a current member, every member is eligible and no device has left the group since that version (a rejoin excepted). Queued messages refused with `KEY_VERSION_STALE` or `KEY_ROTATION_REQUIRED` are sealed again with the newer key, at most three times each.
8. **Leaf refresh.** A member that writes and whose own leaf is at least seven days old commits an empty commit before writing. If that commit fails, the write still goes ahead and the refresh is tried again on a later write.
9. **Rejoin.** A device that cannot process a correctly signed, chain-consistent commit, cannot join from its Welcome, finds a key commitment mismatch, or lost its local group state keeps the version keys it already derived, deletes its group state and publishes a new package as a rejoin request. The next commit by another usable member removes and re-adds it in one commit. The server and the client each allow at most three rejoin requests per device and channel in 24 hours; after that the device shows a plain error. The device itself (once its request has waited 30 minutes) or the conversation's managers can then start the conversation again (step 10).
10. **Fresh start.** Replacing the group with a new one ("start without earlier messages") requires step-up and a device-signed fresh-start intent and is allowed only when (a) no usable member exists or none has been online in the last 72 hours (a member counts as online when it reads the channel's key state or commit log, recorded at most every ten minutes; presence is not used), (b) the caller's device has had an open rejoin request for 30 minutes, or (c) the caller can manage the channel (or is a DM participant) and a pending addition, required removal or rejoin request has waited 15 minutes without an accepted commit. Otherwise the server answers `KEY_FRESH_START_NOT_REQUIRED`; an ordinary `create` on an existing group is refused with `KEY_FRESH_START_REQUIRED`. Every member of the old group leaves it with the new version, and managers (or the other DM participants) are notified. Earlier versions stay unreadable for devices that do not already hold their keys or a recovery-archive copy.
11. **Equivocation and downgrade.** A transcript mismatch, a version below one already verified, a genesis at or below the pinned version, an invalid envelope signature, a directory head that moves back, or a roster that does not match is treated as server equivocation: work stops, the local state is kept and the error is shown instead of retrying into a rejoin. Once a device has verified a group-protocol-4 genesis for a channel, keys for that version and later come only from that group or from recovered keys whose commitment matches the verified envelope; RSA deliveries and protocol-3 locators for those versions are refused (`MLS_DOWNGRADE`), as is a server state with no group. The server serves protocol-3 envelopes only for protocol-3 versions, and `POST /keys` refuses protocol-4 versions.

Devices that are offline do not hold up anyone. When they return they catch up from the commit log, which is kept. A device that is not yet a member (a new device, a device of a user who just gained access, or a device left out of a migrated channel's first group) publishes its package and waits; any online usable member adds it, in the background after a random 2–20 second delay so devices do not race. The new device reads from the version that added it. Messages written between the time it became eligible and the time it was added stay unreadable to it, unless the account's recovery archive holds those versions (backed up by another of the user's devices that was a member). Protocol-1 to protocol-3 history stays readable through the existing delivery paths; new writes always use protocol 4.

A commit with an UpdatePath replaces the committer's own leaf and the path secrets, which adds fresh secrets to the group key. It does not replace any other member's leaf. A device whose stored state was copied is therefore healed only when that device itself commits with an UpdatePath (a writer does so at least every seven days; any member does so when its device happens to commit a removal or the daily refresh) or when it is removed by revoking it. A member that never makes such a commit keeps its leaf until it is removed. This is narrower than protocol 3, where each version was a new group built from fresh packages of all participants. Theft of a long-term P-256 identity key alone does not reveal group secrets, but it allows signing as that device until the device is revoked. Theft of an endpoint's saved version keys or recovery code exposes the history they cover. This implementation does not claim message-level forward secrecy for retained history, post-compromise security for members that do not commit with an UpdatePath, or a completed independent audit of `ts-mls` or the application adapter.

An eligible malicious member can deny service inside a group, for example with a commit whose path secret for one member is wrong, or a Welcome that the new device cannot open; the server cannot see this. Affected devices rejoin. Repeated abuse is attributable through the audit records of committer devices, and is ended by managers removing the member, then a fresh start if needed.

## Passkeys and sensitive actions

Set stable `WEBAUTHN_RP_ID` (hostname only) and exact `WEBAUTHN_ORIGINS`. Production origins must use HTTPS and belong to the RP ID. The defaults derive from configured CORS origins; explicit settings are recommended. RP ID changes strand existing credentials and require an enrollment migration. WebAuthn user verification is mandatory for both registration and authentication. Attestation is not used as an enterprise trust claim.

Challenges last five minutes, are stored in PostgreSQL, bind ceremony/session/account/purpose, and are consumed even for a failed assertion. Credential counters advance atomically with session creation or the step-up grant. Login uses discoverable credentials without returning account-specific credential lists to unauthenticated callers.

Sensitive routes request a two-minute, one-use grant bound to the live session, exact HTTP method/path and canonical body hash. The route classifier uses Express's routed pathname, including absolute-form targets and case/trailing-slash variants. Absolute-form sensitive requests are rejected even with an origin-form grant. Protected operations include device approval/revocation, session revocation, passkey enrollment/deletion, recovery configuration/disable, fresh conversation start, destructive channel/category actions and membership/role/invitation/permission changes. Each grant stores the verified password/passkey snapshot. Consumption rechecks the live approved session and current credential; MLS fresh-start requires a server-created one-use receipt and rechecks that credential inside its key transaction. Resource authorization is still checked after step-up. Infrastructure/audit failures remain 5xx/503 rather than being disguised as failed credentials.

An approved device may use the current password for initial step-up only while the account has no passkey. Once a passkey exists, password fallback is refused. Register a spare authenticator; the last passkey cannot be deleted. Recovery of history does not reset a forgotten account credential or lost passkey. A user changes the password after step-up; every other session of the account ends and grants made with the old password stop working. Step-up purposes bind the method, path and request fields but never password fields, because a purpose is stored with its challenge and grant and a fast digest of a password could be guessed offline. A user with a passkey can turn password login off, which ends the other sessions opened with the password; a correct password then gets the same answer as a wrong one. An operator resets a password with `reset-password`, which also turns password login back on and ends every session. A deployment-wide password-disable policy and organization-enforced authenticator counts are not provided.

## User-controlled history recovery

The client generates 256 random bits, displayed as a recovery code. AES-GCM encrypts a newly generated P-256 recovery signing private key and individual channel-history keys. Associated data binds account, generation, channel, version and key commitment. The approved device signs the recovery public key into its directory; the server never receives the code or unencrypted private material.

The user must record the code before enabling recovery. Enabling and uploading old history are separate, retryable actions. Future keys received on a configured device are backed up automatically. Other devices enable their own backups by entering the same code. Uploads are idempotent and bounded; local completion markers prevent repetitive writes. A failed upload does not stop chat and can be retried with “履歴を保存”. Only accepted account history in currently visible channels is eligible. Restored keys can be saved again under a newly confirmed recovery code.

Encrypted secrets and archived keys require an approved device. A live, bound, non-revoked pending replacement can read only public generation/signing-key metadata. It derives a separate account/generation-bound retrieval capability from the 256-bit code using HKDF-SHA256; the server stores only its SHA-256 hash and checks a bound live device and a 10/hour budget before returning the encrypted secret. The capability is not the archive encryption key and cannot approve a device. After normal account login and retrieval proof, a replacement device decrypts the recovery signing key, verifies its public key against the directory, signs its exact pending identity approval, and imports archived keys. Each recovered key must match its stored commitment. Wrong code, altered ciphertext, account/channel/version substitution and missing membership fail closed. Restoring history does not grant old workspace access or distribute the archive to other accounts.

Disabling recovery requires an approved device, step-up and a signed directory event. It removes the server's archive for that generation and invalidates its approval authority. Local copies already decrypted on devices cannot be remotely erased. To rotate a code, disable it, confirm a new code, then save available history again. Losing all devices and the code permanently loses the corresponding history. No administrator recovery or hidden escrow is available.

## Additional audit hardening (2026-09-17)

Password hashes use bcrypt cost 12–15 followed by a domain-separated HMAC under the independent, mandatory `PASSWORD_PEPPER` (or file-backed equivalent). Only the salt and HMAC are stored. Runtime comparison rejects unprotected/weak legacy formats. Public login/registration have two worker slots, no waiting admissions, and retain their slot through the audit commit; authenticated password verification has a separate two-worker pool with 16 waiting slots. Failed logins include an account ID when known and a keyed normalized-email tag. An exhausted account budget requires a short-lived, source/account-bound one-use work proof, automatically solved in a browser worker. IP budgets still apply. This is bounded admission, not a guarantee against network-scale denial of service.

The server validates native MLS package and leaf signatures, credential identity, lifetime, suite, capabilities and usable encryption keys on package publication and commit admission, including the UpdatePath leaf of a commit. Empty commits require a due refresh (the 24-hour group refresh or the committer's seven-day leaf refresh), and add-only and empty commits are rate limited. Commit-log reads return only versions at which the reading device was a member, plus the version that removed it; roster reads at a version are limited to devices that were members then. Protocol-3 envelope reads remain limited to received epochs and necessary predecessors. Peer directory reads require approved devices and locked channel authorization; former participants expose only the prefix previously used by that channel. Current participants share account-wide public device proofs because device identities are account-wide and prefix signatures require the complete chain. Neither endpoint discloses plaintext group keys.

Permission overrides enforce actor hierarchy and permission subsets for preview, create, update and delete. Same-level conflicts now resolve to deny. `CONNECT_VOICE` controls participation and presence independently of channel viewing; revocation feeds room removal and reevaluation of the devices that may stay in the channel's group. Attachment user quotas are scoped to each workspace. Finding-by-finding remediation is recorded in [AUDIT_ALPARTS_REMEDIATION.md](./AUDIT_ALPARTS_REMEDIATION.md).

## Migration and rollout

- Use the normal verified backup and maintenance-window procedure, then apply migrations through `0015_audit_hardening.sql` with the migration identity. Do not use schema push.
- The migration adds approval/authentication/recovery/MLS tables, builds deterministic `legacy` directory entries, retains existing devices as approved, aborts old provisional epochs and flags active channels for group-protocol refresh. Existing ciphertext/accepted legacy keys are preserved.
- Review the existing device list before rollout. From the trusted migration snapshot, run `pnpm --filter @alparts/server exec tsx src/scripts/export-directory-migration-anchors.ts` and retain its JSON output as a **candidate** inventory. Verify the devices against independently retained owner records, then put the reviewed account heads in `packages/client/src/security/directory-migration-anchors.json` before building all clients. Do not automatically fetch or trust these roots from the live API. The checked-in empty object is for fresh deployments; existing legacy accounts fail closed until their roots are pinned. Pinning cannot retroactively prove that the reviewed inventory was honest.
- Legacy entries stay unapproved until the complete pinned prefix matches, even across pages. A pinned migrated account cannot be replaced with a fresh bootstrap. Pre-fix local directory caches are rebuilt while preserving their previous checkpoint for rollback/fork detection.
- Migration 0015 invalidates outstanding step-up grants and preserves old encrypted recovery data. **Before discarding an approved device**, enter the existing recovery code in that device's recovery screen to enroll the retrieval capability with step-up. Existing codes are retained; no archive deletion or code rotation is required. A pre-0015 configuration with no remaining approved device cannot download its secret until an approved device is available. No password-only bypass is provided.
- Deploy matching server/client bundles together. Existing tabs must reload; old clients cannot continue writing through the legacy group endpoint. Keep approved devices available for the first group after an upgrade (see the group protocol 4 steps below). Configure and verify recovery before destroying an old device profile.
- Before upgrading, independently back up the database, audit checkpoint and secrets. Create a stable, independent password pepper of at least 32 random bytes. Stop all serving processes and run `db:migrate:runtime` with the new secret. Unlike bare drizzle migration, this runner also wraps existing bcrypt hashes without requiring plaintext passwords; the conversion is atomic, bounded in memory and refuses unsupported/weak hashes. Losing/replacing the pepper makes existing password authentication unavailable. Keep it separate from DB backups.
- Migration 0016 normalizes existing email bindings (collisions stop migration), records bounded historical directory grants and adds the voice permission. Existing Owner/Administrator/Member roles retain voice; Guest/Integration/custom roles require explicit grants. Review deny/allow conflicts before deployment because same-level deny now takes precedence.
- Every serving environment requires a configured, provisioned audit checkpoint with `AUDIT_CHECKPOINT_REQUIRED=true` and a durable head in a separate `AUDIT_HEAD_BUCKET`, identified by a stable `AUDIT_HEAD_OBJECT_KEY`. Both are checked after restart; missing heads require explicit operator recovery (see OPERATIONS). New `dev.sh` setups provision it explicitly. Existing setups must preserve and verify their checkpoint; absence is not automatically repaired.
- The schema gate expects 24 migrations (0000–0023) and the PostgreSQL 16 catalog fingerprint recorded in `packages/server/src/db/schema-catalog.ts`. A rollback requires coordinated application/database recovery; do not independently roll the application back over the new directory or group state.
- Web member-package, group-state, unconfirmed own-commit, chain-pin, per-version key, rejoin-count, protocol-3 key-package/proposal, archive and checkpoint records use the existing local-state AES key in `alparts-security`. Desktop local master keys retain the existing OS wrapping boundary. Channel revocation purges channel-scoped records; asynchronous writers check the same lifecycle guard. Logout preserves encrypted records for the same device.

### Group protocol 4 (migration 0023)

1. Use the normal verified backup and maintenance-window procedure: back up the database, audit checkpoint and secrets, stop all serving processes, and run `db:migrate:runtime`. Do not use schema push.
2. Migration `0023_continuous_mls_groups.sql` adds the group tables (`mls_groups`, `mls_member_packages`, `mls_published_package_ids`, `mls_group_members`, `mls_group_node_keys`, `mls_rejoin_requests`). It aborts every pending protocol-2/3 epoch with the same cleanup as before (acknowledgements, then deliveries, then the recipient snapshot) and marks every channel with an active epoch so that its next write needs a group. Accepted keys and ciphertext are preserved, and protocol-1 to protocol-3 history stays readable.
3. Deploy the matching server and client bundles together. Tabs opened before the upgrade get `410 UPDATE_REQUIRED` from the retired per-epoch routes and must reload.
4. After the upgrade, open the app on approved devices. Clients publish a package for every channel they see as soon as channel lists load. A migrated channel's first group waits for every still-eligible device that was a recipient of its last key, until each has published a package or 24 hours have passed since the first package for that channel; then it proceeds with the devices that have packages. Writing in that channel waits until the first group exists. Devices left out are added later by any member when they come online; messages written in between stay unreadable to them unless restored from the recovery archive.
5. The first group's envelope links to the last protocol-3 envelope, so devices that followed the channel before keep a verified chain.
6. Do not roll the application back once clients have joined groups: a client that verified a group for a channel refuses a server that shows none. Rolling back requires restoring the pre-migration database together with the previous application; messages and group changes made after the upgrade are then lost.

## Runtime topology enforcement

Startup acquires a dedicated PostgreSQL session advisory lock before audit verification or listening. A second process using that database exits with `RUNTIME_ALREADY_ACTIVE`. Loss of ownership is sticky: HTTP/Socket.IO admission stops, sockets close, and authoritative writes are rejected. Request admission asks the lease's own session, so a saturated connection pool is not mistaken for a lost lease; a failed check on a pooled connection refuses that operation without ending the process. Each serialized audit operation holds a separate shared transaction lock through checkpoint persistence; a replacement must acquire that lock exclusively before starting. This enforces the single-process deployment; it does not implement shared rate budgets, distributed rooms, HA or multi-region operation. Keep `DB_POOL_MAX >= 2` and budget one extra dedicated connection. Use direct PostgreSQL or session pooling; transaction-pooling proxies cannot preserve session advisory locks. Offline migration/checkpoint tools still require the documented maintenance window with all writers stopped.

## Verification and remaining release work

`pnpm --filter @alparts/server test:account-security` uses `DATABASE_URL` pointing at an isolated `alparts_test` or `alparts_security_test` database with CREATE DATABASE permission. It creates and drops a unique child database, applies all migrations, verifies an upgrade with retained legacy identities/epochs, then runs real HTTP/WebAuthn/MLS/recovery operations and removes its temporary audit checkpoint. It does not use production data.

A Chromium browser smoke test with a virtual user-verifying authenticator also exercised password login, first-device enrollment, message encryption, code creation/backup, passkey registration, approval of a second browser profile using passkey step-up, recovery of historical plaintext, messages under the replacement group epoch, and discoverable passkey login. Hardware/platform acceptance remains separate. This smoke test predates group protocol 4 and has not been repeated against it.

That earlier browser smoke test predates PRF-protected recovery. The new recovery wrapping is covered by Web Crypto tests with simulated PRF outputs and HTTP integration tests for credential ownership and metadata isolation. Physical authenticator acceptance and native WebAuthn integration remain outstanding; native clients can restore using the recovery code. See [the audit remediation record](AUDIT_ALPARTS_REMEDIATION.md) for the current scope and build configuration.

The ordinary PostgreSQL/object-store integration suite creates and advances continuous groups with real `ts-mls` commits while retaining its authorization, file, WebSocket, voice, audit and schema checks: commit ordering and retries, writes on the current version only, package rules, writes stopping until a device without access is removed, and fresh-start permissions. Server unit tests check the admission rules with real commits. Client tests cover create, add, remove and refresh across several simulated devices, offline catch-up, adopting an own commit after a lost response, losing a race, rejoin, joining at a historical directory head, envelope tampering and rollback (stopped as equivocation), exporter agreement, transparency signatures and archive tampering. The HTTP suite uses a synthetic standards-compliant authenticator; it does not substitute a stub for SimpleWebAuthn's verifier.

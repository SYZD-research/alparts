# Phase 1 プロトタイプの運用

[English](OPERATIONS.md) | 日本語

最終更新: 2026-09-04

この文書が対象とするのは、Windows・macOS・Linuxのデスクトップ／Web／単一ノード／チャンネルごとの基本的な鍵／テキスト中心と、最大8人の音声（P2P、またはフレームを端末間で暗号化するセルフホストの SFU 経由）からなるプロトタイプだけです。公開前の脆弱性情報、認証情報、その他の影響の大きい秘密情報を扱うための本番利用の承認ではありません。

## 起動時の前提

1. PostgreSQLとオブジェクトストレージ（推奨はSeaweedFS）に、それぞれ独立した最小権限の認証情報を用意し、リモート接続には認証付きのTLSを使います。
2. 秘密情報は `*_FILE`、systemdのcredential、またはデプロイ環境のシークレット管理から渡します。値をリポジトリ、イメージ、コマンドライン、ログに入れないでください。
3. 移行は、アプリケーションの実行時とは別のデプロイ用IDで、アプリケーションの書き込みを止めた状態で実行します。元に戻せない変更の前には、後述のバックアップの確認を通します。
4. プロセスはroot以外のユーザーで起動し、公開側のTLSは信頼できるリバースプロキシで終端します。PostgreSQL、オブジェクトストレージ、ヘルスチェック、管理用のエンドポイントを公開ネットワークに出さないでください。
5. ヘルスチェックはそれぞれ別のルートで確認します。

   - `/health/startup`: 起動が完了したか。
   - `/health/live`: プロセスのイベントループがHTTPを処理できるか。
   - `/health/ready`: 停止処理中ではなく、PostgreSQL、設定したオブジェクトストレージのバケット（起動後に消えていないことを毎回確認します）、監査チェックポイントが利用できるか。

プロセスは待ち受けを始める前に、監査のHMACチェーン全体を検証します。失敗はセキュリティインシデントです。起動させるために、監査の行やチェックポイントを書き換えたり削除したりしないでください。

サーバーの待ち受けアドレスはIPアドレスの表記だけを受け付け、`BIND_HOST` が未設定の場合は `127.0.0.1` に限ります。systemdユニットの例もループバックに固定しています。コンテナーイメージの既定もループバックで、本番用のCompose構成だけが、コンテナーネットワーク内で `BIND_HOST=0.0.0.0` を明示し、ホスト側では `127.0.0.1` に公開します。必ずTLSのリバースプロキシとネットワークポリシーを前段に置いてください。オブジェクトストレージへのリクエストには `S3_REQUEST_TIMEOUT_MS`（既定は10秒）の絶対的な期限があり、オブジェクトの一覧取得も、件数、キーのバイト数、プレフィックスの文法、絶対的な期限で制限します。添付ファイルのダウンロードでは、GETの応答の長さを保存時のサイズと照合し、そのサイズを超えるデータをクライアントへ送りません。

新規登録では、入力されたメールアドレスに6桁の確認コード（15分間有効、5回間違えると無効）を送り、そのアドレスの持ち主であることを確かめます。送信には `SMTP_HOST`・`SMTP_FROM`（必要に応じて `SMTP_USER`・`SMTP_PASSWORD_FILE`）を設定します。本番では `SMTP_SECURE=true`（最初からTLS）またはSTARTTLSが必須で、証明書を検証します。本番で `SMTP_HOST` が未設定の場合、既存のアカウントのログインはそのまま使えますが、新規登録は `EMAIL_VERIFICATION=disabled` で確認を明示的に無効にしない限り拒否し、起動時に `registration.unavailable` の警告を出します。開発環境では、SMTPがなければメールをメモリーに保持してログに出力します。すでに登録済みのアドレスには、コードではなく案内のメールを送るため、応答からアカウントの有無はわかりません。この変更より前に作成されたアカウントのメールアドレスは確認されていません。

登録用のメールは日本語または英語で送ります。クライアントはアプリで選んだ言語を `Accept-Language` として送り、サーバーはその中で最初に対応している言語を使います（どちらもなければ英語）。設定は不要です。

音声通話では、`VOICE_ICE_SERVERS_JSON` に、運用者が管理するSTUN/TURNを最大4件までJSONで設定できます。既定の空の配列では第三者のサービスに接続しない代わりに、直接の候補で到達できないNAT間の通話を保証しません。TURNの認証情報は通話に参加するクライアントへ渡るため、サービスの管理者の認証情報を流用せず、短期間だけ有効な最小権限の認証情報を発行してください。TURNでは認証付きのTLS（`turns:`）を優先し、公開インターネットに無制限の中継として開放しないでください。P2Pのメッシュは最大8人で、水平にスケールするメディアサーバーの構成ではありません。

`VOICE_SFU_ENABLED=true` にすると、そのデプロイメントの通話はすべて、P2P のメッシュではなくサーバー自身の mediasoup の SFU を経由します。設定はサーバーの起動時に反映されます。クライアントは音声の各フレームを端末から出る前に暗号化し、誰かが参加・退出するたびに鍵を替えるため（[ADR 0014](./adr/0014-sfu-frame-encryption.md)）、SFU が転送するのは暗号文だけです。フレームを暗号化できないブラウザーは通話に参加できず、アプリがその旨を利用者に伝えます。`VOICE_SFU_ANNOUNCED_ADDRESS` にクライアントから到達できるサーバーのアドレスを設定し、`VOICE_SFU_BASE_PORT` から worker の数（`VOICE_SFU_WORKERS`）だけのポートへの UDP と TCP を許可してください。これらのポートは、ホストが一時的な通信に使うポートの範囲（Linux では `net.ipv4.ip_local_port_range`。既定は 32768〜60999 で、40000 も含まれます）から外すか、`net.ipv4.ip_local_reserved_ports` で予約してください。そうしないと、その worker で最初の通話が始まるときにほかのプログラムが一時的にポートを使っていて、その通話が失敗することがあります（次の通話は同じポートで再び試します）。参加者どうしは互いのネットワークアドレスを見なくなりますが、サーバーは誰が通話にいるかと、誰がいつ話しているかを見られます。通話の上限は引き続き8人です。

添付ファイルのデータベースの行と、オブジェクトストレージ上のオブジェクトは、分散トランザクションではありません。アップロードの状態の確認では、データベース内で認可とチャンクのメタデータのスナップショットを取り、データベースの接続とロックを解放してから、オブジェクトを照合します。その後のチャンクのPUTと完了処理では、改めてロックと認可を取得します。データベースの失敗後に残ったオブジェクトは、期限切れの後片付けで回収します。ダウンロードの開始後に権限を失っても、送信を始めた暗号文のストリームを途中で取り戻すことはできません。これらを、ストアをまたいだアトミックなコミットやリモートでの消去と説明しないでください。

## 監査チェックポイント

2026-09-30以降は、ローカルのチェックポイントに加えて、別のオブジェクトストレージのバケットに最新の署名済みのheadを保持します。`AUDIT_HEAD_BUCKET`（既定は `${S3_BUCKET}-audit`）と `AUDIT_HEAD_OBJECT_KEY`（デプロイごとに固定した識別子）を設定します。通常の起動では、欠けているheadを作成しません。データベースとチェックポイントのファイルの両方を過去に戻しても、このheadが保持されていれば、再起動時に拒否します。

監査 head 移行手順（既存のデプロイ）:

1. アプリを停止し、独立して保管している記録と、現在の監査チェーンが一致することを確認します。初期化コマンドのHMACの検査だけでは、移行前に起きた、正しく署名された末尾の切り詰めを見分けられません。
2. 通常の画像・添付ファイルとは別の `AUDIT_HEAD_BUCKET` を作成します。アプリには、このバケットの `s3:GetBucketLocation` と `s3:ListBucket`、対象のheadの `s3:GetObject` と `s3:PutObject` を許可します。削除の権限は不要です。データベースやチェックポイントのファイルを修復する担当者と、バックアップの復元に使うIDには、headの書き換えや削除の権限を与えないでください。
3. 固定した `AUDIT_HEAD_OBJECT_KEY` とバケットを環境設定に保存し、通常と同じデータベース、監査の鍵、チェックポイントのパスで、`pnpm --filter @alparts/server audit:head:init` を一度だけ実行します。配布イメージでは `node packages/server/dist/scripts/initialize-audit-head.js` を使います。既存のheadは上書きしません。新規のデプロイでは、`audit:checkpoint:init` が両方を作成します。
4. 再起動して、readinessを確認します。以降は、識別子とバケットを起動のたびに変えないでください。headを通常のデータのバックアップと一緒に過去へ復元しないでください。headが欠けたときに、初期化を自動で再実行しないでください。

更新の順序は、データベースのコミット → ローカルのチェックポイントのfsyncとrename → headの保存です。途中で障害が起きると、次の書き込みを止めます。ローカルのチェックポイントがheadより進んでいる状態は、再起動時にチェーン全体と両方のアンカーを検証してから前に進めます。チェックポイントとheadの読み取りも監査の書き込みと直列化し、正常な同時更新を巻き戻しと誤って判定しないようにしています。

この追加のバケットはWORMではありません。データベース、ローカルのファイル、headのすべてを書き戻せる管理者や、サーバー全体の侵害は別の能力で、局所的な検証だけでは同時の巻き戻しを見分けられません。独立した外部証跡（witness）は引き続き利用できます。headを保存する前に停止したコミットや、witnessより後の記録についての既存の限界は変わりません。通常のバックアップと復元は `S3_BUCKET` だけを扱うため、headは含まれません。headは独立して保全してください。

データベースの最新の監査の行の削除を検出するには、`AUDIT_CHECKPOINT_PATH` を、PostgreSQLの運用者とは書き込み・削除の権限を分けたマウントまたはストレージに置きます。このファイルはHMACで認証され、監査のコミット後にアトミックに更新されます。初めてのデプロイでは、サーバーを停止したまま、本番と同じデータベース、`AUDIT_INTEGRITY_KEY`、チェックポイントのパスを設定して、`pnpm --filter @alparts/server audit:checkpoint:init` を一度だけ実行します。その後、`AUDIT_CHECKPOINT_REQUIRED=true` でサーバーを起動します。既存のチェックポイントがある場合、このコマンドは上書きしません。

必須モードでは、チェックポイントの欠落（空のチェーンを含む）、参照する行やハッシュの不一致、巻き戻し、末尾の切り詰め、チェックポイントの読み書きの失敗のいずれでも、起動、readiness、権威的な書き込みを安全側に失敗させます。メッセージの作成・編集・削除・再送、リアクションとピン留め、個人設定とブックマーク、セキュリティと管理の変更は、状態の変更と監査の行を同じトランザクションに入れます。既読位置と、仮のアップロードのチャンクのメタデータや後片付けは、専用の監査イベントを増やしませんが、同じプロセス内の受付制御を通ります。通常の追記とチェックポイントの更新は、同じPostgreSQLのadvisory lockの中で、現在のアンカーのHMACと、データベースの末尾への子孫関係を検証し、外部のファイルは比較対象が変わっていない場合にだけアトミックに置き換えます。完全性の失敗はプロセス内で解除されず、通常のサーバーの起動や監査の追記で、欠けたチェックポイントや切り詰められた末尾を作り直したり、署名し直したりすることはありません。欠けたときに再び初期化すると、切り詰められた後のチェーンを新しい正しい履歴として承認してしまうため、インシデント対応で、独立して保管したチェックポイントやバックアップと照合するまでは実行しないでください。

状態の変更と監査の行は同じデータベースのトランザクションでコミットするため、その直後のチェックポイントの入出力だけが失敗した場合、すでにコミットした変更は成功として一度だけ返します。以降の、監査対象または保護対象の権威的な変更とreadinessは、安全側に失敗します。ストレージの一時的な障害など、完全性の失敗ではないチェックポイントの入出力の失敗は、次の変更またはreadinessの確認の時点で（最短で2秒間隔）、同じチェーンの検証付きで書き直し、成功すれば自動的に受け付けを再開します。完全性の失敗は引き続き解除されず、運用者による復旧が必要です。監査のheadの読み書きには、利用者のダウンロードと共有しない専用のオブジェクトストレージの接続と同時実行枠を使います。運用者は「500が返ったからデータベースも巻き戻った」と推測して再試行しないでください。在席状況と端末の最終利用時刻は、認可などには使わない参考用のテレメトリーで、受付制御の対象外であり、欠落を許容します。readinessの失敗後は受け付けを停止し、このテレメトリーの更新を、サービスの書き込みが成功したことと解釈しないでください。この仕組みはプロセス内の受付制御を使うため、複数のアプリケーションプロセスには対応していません。

ローカルのsystemdの `StateDirectory` は、事故によるデータベースの行の削除の検出を改善しますが、同じホストや運用者がデータベースとファイルの両方を削除できるなら、運用者の分離にはなりません。独立したマウントを使わない構成で「運用者から独立した監査」と主張しないでください。

`AUDIT_INTEGRITY_KEY` は、監査のチェーンとチェックポイントの検証に必要です。データベースのダンプと同じ認証情報や、同じ暗号化コンテナーにだけ保存するのではなく、別の暗号化された資産として復旧できるようにしてください。

## systemd

ビルド済みのリポジトリを `/opt/alparts` に置き、`deploy/alparts.service` を `/etc/systemd/system` にインストールします。ユニットの例は、`/usr/bin/node` にNode.js 24以降があることを前提にしています。別の場所にインストールした場合は、起動前に `ExecStart` をその確認済みの絶対パスに変更し、`systemd-analyze verify /etc/systemd/system/alparts.service` を実行してください。rootが所有する認証情報のファイルを、1つの秘密情報につき1ファイルとして `/etc/alparts/credentials` に置き、秘密ではない接続先やポリシーだけを `/etc/alparts/alparts.env` に置きます。ユニットの例が作成する `/var/lib/alparts-audit` は、データベースの運用者からの分離を主張する前に、独立して保護された保存先へbind mountしてください。

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now alparts.service
systemctl status alparts.service
curl --fail http://127.0.0.1:3000/health/ready
```

## 安全な移行の手順

移行のスクリプトとバックアップのスクリプトは、互いを自動で実行しません。運用者が次の順序を明示的に管理します。

1. まず、デプロイするリビジョンの型チェック、テスト、ビルドと、新しい使い捨てのデータベースへの移行を検証します。
2. アプリケーションの受け付けを止めて停止し、データベースとオブジェクトストレージへの書き込みを止めます。バックアップの間に書き込みがないことは、運用者が保証します。
3. ageの受信者、バックアップ用のデータベースの読み取りID、オブジェクトストレージの読み取りID、出力先を設定し、移行のラベルを付けて確認を実行します。

   ```bash
   export ALPARTS_BACKUP_QUIESCED=YES_WRITES_ARE_STOPPED
   scripts/pre-migration-backup.sh 0006_example_change
   ```

4. 出力された成果物を、本番とは別の空のデータベースと空のバケットに `scripts/restore-verify.sh` で復元して検証します。`VERIFIED <run-id>` が得られない場合は、移行に進まないでください。
5. バックアップの成果物のダイジェストと検証結果を、独立した変更記録に残します。
6. アプリケーションの実行時とは別のデプロイ用IDで、移行を実行します。

   ```bash
   pnpm --filter @alparts/server db:migrate:runtime
   ```

7. アプリケーションを起動し、startup・live・ready、監査の完全性、移行の記録、PostgreSQL 16の `public` カタログのフィンガープリントを確認します。フィンガープリントの不一致を、期待値の書き換えで回避しないでください。スキーマのずれを調査し、前向きの修正か、検証済みの復元を行います。巻き戻しや復元が必要な場合は、新しい隔離された環境で原因を確認してから、承認済みの手順書を使ってください。

`pre-migration-backup.sh` は、移行、サービスの停止、復元、後片付けを実行しません。`restore-verify.sh` は、既存のスキーマを削除せず、既存のバケットを消去せず、本番らしい復元先の名前を拒否します。環境設定と手順全体は [BACKUP.ja.md](./BACKUP.ja.md) を参照してください。

## 正常な停止

`SIGTERM` と `SIGINT` を受け取ると、ただちにreadinessを失敗させ、新しいAPIの処理を拒否し、リアルタイム通信のクライアントを切断し、バックグラウンドの後片付けを止め、HTTPの接続を最大25秒かけて処理し終えてから、データベースの接続プールを閉じます。systemdユニットは、強制終了まで30秒を許容します。

停止を、バックアップのための書き込み停止の仕組みとして暗黙に扱わないでください。データベース、オブジェクトストレージ、管理ツールを含めて、書き込み元が止まったことを別途確認してください。

## メトリクスとアラート

`/metrics` は、`METRICS_ENABLED=true` の場合にだけ登録します。`METRICS_TOKEN`、または権限を保護した `METRICS_TOKEN_FILE` に、32バイト以上の値が必須で、Bearerトークンを一定時間で比較します。トークンがあっても、このエンドポイントを公開のルートに出さないでください。

収集するのは、HTTPのリクエスト数・ステータス・応答時間、データベースの接続プールの合計・待機中・空き・上限、パスワード処理とオブジェクトストレージの受付枠の使用中・待ち・上限、イベントループのp50・p99・最大、プロセスのメモリーと稼働時間です。外部の監視で、ディスクとinode、PostgreSQL、オブジェクトの容量、TLS証明書の期限、バックアップと別ホストへのコピーと復元、systemdの再起動、暗号化された読み書きの合成監視を追加してください。ログは、UTCの構造化JSONで、リクエスト・トレース・操作者・テナントの情報を持ちますが、本文、トークン、パスワード、鍵、平文は出力しません。

## 単一ホストでの自動バックアップ

`deploy/alparts-backup.timer` は、毎日、ランダムな遅延付きの永続タイマーで、一度だけ実行するサービスを起動します。`scripts/backup-under-systemd.sh` は、flockで重複を拒否し、対象のサービスが稼働中でなければ何も変更せずに失敗し、アプリを止める前に `backup.sh --preflight` で必要なコマンド（rclone 1.75.1以降を含む）と設定を確認し、停止した後にだけ書き込み停止の宣言を設定します。成功・失敗・シグナルのいずれでも、trapでサービスの再起動を試みます。バックアップのユニットは自らアプリを停止するため、アプリへの `Requires=` の関係を持たせないでください。

保持期間の処理は、バックアップの成功とアプリの再起動の後にだけ実行します。`scripts/prune-backups.sh` は、既定でドライランになり、範囲の狭い既存のディレクトリ、正確なファイル名、日数と最低限のコピー数、`BACKUP_PRUNE_ACK=DELETE_EXPIRED_ENCRYPTED_BACKUPS` を必要とします。タイマーの成功だけでは災害復旧にならないため、成果物の別ホスト・別リージョンへのコピーと、復元のテストを別に監視してください。

## バックアップと復元の範囲

バックアップのツールは、次のものを1つの実行IDにまとめます。

- `--format=custom --serializable-deferrable` によるPostgreSQLの論理ダンプ。
- 設定したバケット内の、最新のオブジェクトのデータ。
- テーブルごとの行数、添付ファイルとオブジェクトの参照、オブジェクトの一覧、SHA-256チェックサム、マニフェスト、ツールのバージョン。

平文の作業ファイルは、モード `0700` の `mktemp` ディレクトリの下にだけ作成してtrapで削除し、公開する成果物はageの受信者の公開鍵に対して暗号化します。既存の出力ファイルは置き換えません。PostgreSQLとオブジェクトストレージには共通のトランザクションがないため、書き込みを止めずに取ったバックアップは、整合したスナップショットではありません。

復元の検証では、次を強制します。

- `alparts_restore_*` / `alparts_verify_*` のデータベースと、`alparts-restore-*` / `alparts-verify-*` のバケットだけを許可し、本番らしい名前や、元のバケット・既定のバケットを拒否します。
- システム以外のスキーマやオブジェクトがないデータベースと、オブジェクトがないバケットだけを許可します。
- 復元先の所有者が `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` で、危険な組み込みロールを引き継げないことを確認します。
- ファイルシステムへ展開する前に、アーカイブのエントリー数、各通常ファイルの論理的なバイト数、展開後の合計バイト数を、設定した上限と照合します。GNU tarが示す展開後のサイズを使い、圧縮されたスパースや未対応のメタデータを検出できる場合は拒否します。
- 復号 → アーカイブ・パス・種類の検証 → チェックサムの確認 → 1つのトランザクションでの `pg_restore` → オブジェクトのコピー → すべてのテーブルの行数、添付ファイルの参照、オブジェクトのキー・サイズ・SHAを再ダウンロードして比較、の順に行います。

PostgreSQLへの接続は、モード `0600` のlibpqのサービスファイルとセクション名で渡し、オブジェクトストレージの認証情報は、シェルの組み込みコマンドで、モード `0600` の一時的な `rclone` 設定ファイル（モード `0700` の作業ディレクトリの下）に書き込みます。パスワード、アクセスキー、シークレットキーを、子プロセスのコマンドライン引数や環境変数で渡さず、`RCLONE_*`・`AWS_*` の環境変数も子プロセスから取り除きます。復元時の展開後のバイト数の上限は、保護された作業用のファイルシステムのクォータと、安全に使える空き容量以下に設定してください。

### 確認済みの往復テスト

2026-08-26に、既存のデータベース、バケット、ボリュームを使わない一意のPostgreSQL 16とMinIOの環境で、`backup.sh` から、権限を持たない空の検証用データベースと空のバケットへの `restore-verify.sh` までを完了しました。

2026-10-02に、オブジェクトストレージをSeaweedFS 4.47に、転送ツールをrcloneに置き換えた後、一意のPostgreSQL 16とSeaweedFSの環境で、同じ `backup.sh` → `restore-verify.sh` を完了しました（43テーブル、プロフィール画像の参照を含む2オブジェクト、74,096バイト）。

- 実行ID: `20260826T144441Z-c50148de2d3e`
- データベース: 4テーブルで、元と復元先の行数が一致
- オブジェクト: 2オブジェクト、合計144バイト
- 検証: マニフェスト、ペイロードのチェックサム、添付ファイルの参照、オブジェクトの一覧、再ダウンロードのSHAが一致

この結果が示すのは、その成果物のデータベースの行と、最新の暗号化されたオブジェクトのデータを、検証用の復元先に再現できたことだけです。アプリケーションの起動、元の監査の鍵でのチェーンの検証、ブラウザーの端末の鍵によるテストデータの復号、クライアントでの添付ファイルの一連の操作、RTO/RPOは検証していません。

### バックアップに含まれない資産

- `AUDIT_INTEGRITY_KEY`、ageのID、デプロイ・オブジェクトストレージ・PostgreSQLの認証情報。
- リバースプロキシ、systemd、環境設定とポリシーの設定。
- 外部の監査チェックポイントのファイルと、その独立した保管先の記録。
- ブラウザーの端末の秘密鍵と、チャンネルの鍵のクライアント側の復旧用データ。
- オブジェクトのバージョン履歴、バケットのポリシー、ライフサイクル、タグ、すべてのオブジェクトのメタデータ。

これらは、必要性と権限を分けて、それぞれ別に暗号化して保管してください。ブラウザーの端末の秘密鍵をサーバーのバックアップに加えて、エンドツーエンド暗号化の復旧ができるように見せかけないでください。

## 提供していない運用上の保証

このリポジトリは、PITRやWALの継続的なアーカイブ、WORMやオブジェクトロック、別拠点への自動複製、定期的な自動復元、アプリケーション全体の自動復旧、フェイルオーバー、高可用性、実施済みの四半期ごとの災害復旧訓練、実測したRTO/RPO、72時間の連続稼働試験を提供しません。安全側のローカルでの保持と、毎日のsystemdによる定期実行は実装しましたが、同じホスト内だけでは災害復旧になりません。監査記録の外部のSIEMやWORMへの転送、データの保持と書き出し、署名付きの更新とリリースの出所の証明も未実装です。

これらは [LIMITATIONS.md](./policies/LIMITATIONS.md) にある正式リリースの阻害要因で、手動でのバックアップの往復テストが成功しても解除されません。
